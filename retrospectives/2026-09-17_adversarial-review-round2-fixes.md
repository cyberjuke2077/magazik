# Исправления второго адверсариального ревью - 2026-09-17

## Задача

Локально устранить подтверждённые дефекты R2-01 - R2-14: потери и дубли заявок,
расхождение корзины с каталогом, неточный поиск, повреждённое клиентское
хранилище, инъекцию в `mailto:`, слабый жизненный цикл административной сессии и
недостаточную защиту login.

## Как решали

- Разделили намеренную новую заявку и повтор операции после потерянного ответа.
  Добавили двухчасовой черновик и снимок операции в `sessionStorage`, квитанцию,
  локальную историю и безопасную страницу статуса.
- Версионировали корзину, добавили runtime-проверку и серверную сверку товаров,
  цены и minOrder перед итогом и отправкой.
- Исправили денежный формат, семантику блока похожих товаров, действие кнопки
  добавленного товара, поиск по производителю и стабильный tie-breaker выдачи.
- Перенесли отзыв административной сессии в БД. Proxy оставили быстрой
  оптимистичной проверкой подписи, полную проверку сессии выполняет DAL на
  страницах и в Server Actions.
- Для публичных форм добавили сетевой attempt-limit до валидации и lookup без
  общего app-wide лимита. Login защищён глобальным, сетевым и account-лимитами.
- Добавили стабильный fingerprint отправляемой корзины, блокировку двойного
  submit, корректные route metadata и дату поставки по московскому календарю.
- Добавили детерминированную migration runtime grants и проверили её на чистой
  изолированной PostgreSQL под ролью без LOGIN и повышенных прав.

## Результат

Локально завершено. R2-01 - R2-14 закрыты цепочкой commits `08a6e64`, `bf3616f`
и `5316955`; последний является вершиной кодовой части кандидата. Финальный adversarial
diff-review не нашёл новых P0-P2.

Проверки: unit - 49 файлов и 388 тестов; readiness integration - 1 файл и 9
тестов; targeted E2E - 17 passed и 1 skipped; полный функциональный E2E - 63
passed и 1 skipped; TypeScript, ESLint, webpack production build и `git diff
--check` прошли. Все 12 миграций применились к чистой изолированной PostgreSQL,
а runtime-права проверены отдельными CRUD-пробами. Browser smoke подтвердил поиск
по производителю, оптовую цену, переход в корзину, клиентские title и минимум
даты поставки.

Визуальный baseline не принят: эталонные снимки используют другой fixture
каталога, а финальный E2E работал на трёх детерминированных seed-товарах.
Production не менялся, ветка не отправлялась, PR не создавался.

## Что можно было сделать лучше

Пути с `()` и `[]` дважды попали в shell без корректного quoting. Временный
TypeScript-скрипт сначала использовал top-level await в CJS-контексте. Первый
вызов browser-act использовал синтаксис другой версии CLI. Turbopack build в
Codex sandbox попытался открыть внутренний порт и упал, поэтому итоговая сборка
проверена через webpack. Два E2E-теста сначала проверяли несуществующее состояние
и не ждали завершения первой навигации.

Предлагаемые правила для `AGENTS.md`:

- `Rule: Пути с (), [] передавать в shell отдельными quoted arguments | Why: zsh globbing остановил диагностические команды.`
- `Rule: Временные TS-скрипты с await запускать через async main() | Why: top-level await не запустился в CJS-контексте.`
- `Rule: Перед запуском browser-act сверять CLI --help для установленной версии | Why: команда browser real из старого синтаксиса отсутствовала в v1.4.2.`
- `Rule: В Codex sandbox production build запускать через npm run build -- --webpack | Why: Turbopack panic при попытке bind внутреннего порта.`
- `Rule: После browser navigation в Playwright ждать конкретный URL перед следующим click | Why: два последовательных pagination click остались на page 2.`
- `Rule: Async-тесты cart storage обязаны await мутации и итоговое состояние | Why: Promise API может пройти формально без проверки результата.`
- `Rule: Для полной замены файла через apply_patch использовать один Update File | Why: Delete File и Add File одного пути в одном patch были отклонены.`

## Границы и следующий шаг

- Не применять к production миграции submission outbox, `AdminSession` и runtime
  grants без проверки точного Supabase target, checksum и отдельного разрешения.
- На Vercel подтвердить trusted ingress, перезапись forwarding headers и
  отсутствие прямого обхода до приёмки rate limit.
- Под runtime-ролью production проверить RLS/GRANT на известных строках, затем
  scheduler, реальное Telegram/email уведомление и backup/restore.
- Отдельно закрыть R2/PII region и юридические реквизиты.
- Первое следующее действие - review локальных commits. После него владелец
  отдельно решает, разрешать ли push/PR и production acceptance.
