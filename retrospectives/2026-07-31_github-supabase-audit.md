# Аудит GitHub и Supabase после работы соразработчика

## 1. Задача

Проверить, действительно ли новая версия проекта находится на GitHub, безопасно сравнить её с локальной копией и подтвердить состояние облачной Supabase без изменения данных и схемы.

## 2. Как решали

- Получили свежие remote refs и сравнили `main` с ветками соразработчика.
- Проверили граф коммитов, состав изменений и служебные ссылки Pull Request.
- В отдельном временном checkout запустили unit-тесты и lint для ветки `codex/parser-trial-limit`.
- Production-сборку проверили на том же коммите в основном checkout и вернули локальную копию на `main`.
- Через Supabase выполнили read-only проверку единственного проекта, доступного текущей авторизации. После уточнения пользователя отдельно сверили организацию этого проекта с целевой организацией разработчика.

## 3. Результат: частично

- Локальный `main` и `origin/main` совпадают на `9d281e3`. Новая работа не объединена в `main`.
- Кодовая ветка `codex/parser-trial-limit` находится на `cc6d459`. Она прошла 212 unit-тестов, lint без ошибок и production-сборку.
- Отдельная ветка `codex/test-commit` находится на `04a95af` и содержит документацию общей Supabase. Ветка расходится с кодовой веткой и представлена отдельным Pull Request.
- Текущая Supabase-авторизация видит только `cyberjuke2077's Org/electromagaz`. В этом проекте подтверждены 7 применённых Prisma-миграций, 12 прикладных таблиц и таблица истории миграций.
- В проекте `cyberjuke2077's Org/electromagaz` RLS выключен на всех 13 таблицах `public`, RLS-политик 0, роли `anon` и `authenticated` имеют права `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` и `TRIGGER` на все 13 таблиц.
- Пользователь уточнил, что новая общая база разработчика находится в `37Lunar's Org`. Эта организация не видна текущей Supabase-авторизации, поэтому её таблицы, миграции и RLS пока не проверены. На новую базу нельзя переносить выводы из старого проекта.
- База, GitHub и локальные файлы не изменялись. Локальная рабочая копия возвращена на чистый `main`.

## 4. Что можно было лучше

До аудита нужно было сначала сверить organization и project ref, а уже затем запускать advisors и проверять `pg_policies`. Новые ветки следовало объединить через один проверяемый Pull Request, чтобы на GitHub была одна кандидатная версия, а не две расходящиеся.

## 5. Изменения во втором мозге

Добавлено правило `verify-live-supabase-security`: до проверки безопасности Supabase обязательно сверять organization, project ref и назначение среды. Исправление RLS и прав не выполнялось. Новая база в `37Lunar's Org` остаётся непроверенной до получения доступа через корректную Supabase-авторизацию.
