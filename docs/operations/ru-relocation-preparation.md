# Подготовка переноса, без запуска production

## Решение владельца - 2026-09-18

Направление: перенос в российскую инфраструктуру. Сервера и аккаунта пока нет.
Владелец отдельно уточнил: магазин ещё не готов к production. Поэтому сейчас
готовим локальную версию и материалы, не покупаем сервер и не переносим данные.
Следующий инфраструктурный этап - изолированный staging с синтетическими данными.

## Техническая схема для проверки на staging

Один nginx с TLS принимает внешние запросы, Next.js слушает только 127.0.0.1:3000.
PostgreSQL доступен по приватной сети только приложению и отдельному оператору.
Next.js, PostgreSQL, логи, резервные копии и средства мониторинга с данными заявок
должны входить в выбранный российский контур. Перенос только БД при сохранении
обработки форм в Vercel не выполняет эту техническую цель.

Текущая база - PostgreSQL **17.6**, а не 16: подтверждено Supabase API 18 сентября.
Для целевой БД и pg_dump/pg_restore нужен PostgreSQL 17 или совместимая более новая
версия; не планировать перенос pg_dump 17 в PostgreSQL 16.

Зависимости от Supabase Auth/Storage в пользовательском потоке нет: сервер
работает с PostgreSQL через Prisma. Публичные изображения Cloudflare R2 можно
оценивать отдельно; контакты, заявки, документы клиентов и дампы туда не помещать.
Проверить все внешние обработчики и договоры отдельно: российский адрес сервера
сам по себе не является подтверждением правового соответствия.

## Подготовленные файлы

- `deploy/nginx/electromagaz-proxy.conf` переписывает X-Forwarded-For и X-Real-IP
  из `$remote_addr`, удаляет X-Vercel-Forwarded-For и Forwarded. Не использовать
  `$proxy_add_x_forwarded_for`: входная подделка окажется первым IP в цепочке.
- `deploy/nginx/site.conf.template` - шаблон прямого TLS ingress. Перед установкой
  заменить зарезервированный домен и пути сертификатов. Default server отклоняет
  неизвестные Host/SNI. Это не готовый конфиг выбранного сервера.
- `deploy/systemd/electromagaz.service` - шаблон запуска от непривилегированного
  пользователя и только на loopback. Проверить путь Node, создать `.next/cache`
  и выдать запись только туда. Сборку выполнять отдельно от runtime.
- `scripts/check-ingress.mjs` поднимает настоящий nginx с echo-upstream без
  публикации портов; проверяет поддельные IP/Host/Proto и удаляет тестовый контейнер.

```sh
node scripts/check-ingress.mjs
```

Контракт proxy_set_header сверён с
[документацией nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header).
Тест доказывает переписывание заголовков, но не конфигурацию firewall, TLS, systemd
или доверие к будущему LB/CDN. Если перед nginx появится ещё один proxy, пересмотреть
всю цепочку; не добавлять доверие к произвольному входящему X-Forwarded-For.

## Порядок будущего переноса

1. Выбрать провайдера, регион, сервер/managed PostgreSQL, домен и владельца
   эксплуатации. Задать допустимые потерю данных и простой, срок хранения и
   удаления заявок, получателя уведомлений. Значения пока не согласованы.
2. Собрать staging из конкретного commit с lockfile, Node 22 и PostgreSQL 17.
   Секреты выдавать вне Git; runtime.env в systemd хранить вне checkout с правами
   0600. Не копировать локальный `.env` и не использовать superuser для приложения.
3. На пустом staging применить всю историю Prisma, завести отдельную runtime-роль
   `electromagaz_app`, проверить known-row SELECT и операции создания/изменения
   заявки, а также отказы доступа к служебным таблицам и DDL. Health недостаточно.
4. Проверить backup/restore сначала на синтетических данных, потом после отдельного
   разрешения на защищённой копии реальной БД. Дамп держать зашифрованным вне Git,
   с ограниченным доступом; сохранять checksum, таблицы/количества и результат
   восстановления. Не переносить весь Supabase cluster вместе со служебными схемами.
5. Реальный перенос планировать отдельной задачей: inventory public schema, ролей,
   расширений, RLS/policies и sequence; `pg_dump --format=custom --schema=public
   --no-owner --no-acl`, восстановление с `--exit-on-error`, затем проверка grants
   и RLS. Команды подключения готовить под выбранные source/target, не вставлять
   пароли в argv или отчёт. Нужен pg_restore review до выполнения.
6. Сверить `_prisma_migrations` и checksum, применить только отсутствующие миграции
   `20260917021149_submission_outbox`, `20260917230000_add_admin_sessions`,
   `20260917233000_ensure_runtime_role_grants`. Не редактировать старые миграции.
7. Настроить cron вызов `/api/cron/notifications` с отдельным CRON_SECRET >=32
   символов. Секрет не помещать в командную строку или логи. Период выбрать по
   проверенной пропускной способности очереди; один вызов обрабатывает до 4 jobs.
   Реальную Telegram/email доставку тестировать только после согласования получателя.
8. До переключения проверить: поддельные IP не обходят лимит; порт 3000 и БД
   недоступны извне; TLS/Host/Origin; статусы с bearer URL не пишутся в access log;
   cookies secure, отзыв сессии; полный desktop/mobile buyer flow; retry/outbox;
   backup alerting, disk limits и восстановление. Error logs тоже проверить на
   токены/ПДн и ограничить доступ/срок хранения.
9. При согласованном запуске остановить приём заявок и workers старого контура,
   сделать финальную копию, восстановить и сверить данные, затем переключить DNS.
   Не допускать двух независимых писателей. Старые admin sessions отозвать.
10. Откат после новых записей в целевой БД требует переноса дельты заявок и очереди.
    Простое переключение DNS назад теряет новые обращения. До запуска отрепетировать
    эту ветку и только потом назначать окно. После подтверждения результата закрыть
    старый доступ, сменить секреты и согласовать удаление старых данных/копий.
