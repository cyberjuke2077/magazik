## 1. Обзор

Система автоматического сбора полных данных о 75,706 электронных компонентах из Excel файлов. Система имитирует поведение реальных пользователей для предотвращения блокировок, работает параллельно в нескольких сессиях и предоставляет красивый TUI интерфейс для мониторинга.

### 1.1 Цели

- Собрать **100% данных** для всех 75,706 товаров
- Завершить сбор за **10-14 дней** (работа 24/7)
- **Избежать блокировок** на всех источниках данных
- Обеспечить **прозрачность** процесса через TUI интерфейс
- Возможность **остановки/возобновления** в любой момент

### 1.2 Требуемые данные для каждого товара

1. **Фотографии** - минимум 1 качественное изображение
2. **Технические характеристики** - все параметры (напряжение, ток, корпус и т.д.)
3. **Datasheet** - ссылка на PDF документацию
4. **Описание на русском** - текстовое описание товара
5. **Цена и наличие** - актуальные данные с российских дистрибьюторов

### 2.2 Компоненты

#### 2.2.1 TUI Interface (Rich)

**Назначение:** Красивый интерфейс в терминале для мониторинга и управления

**Функции:**
- **Progress Bars** - прогресс для каждой сессии и общий прогресс
- **Statistics Panel** - обработано/осталось, успешно/ошибки, скорость
- **Activity Log** - текущие действия каждой сессии в реальном времени
- **Controls** - горячие клавиши (P=пауза, R=продолжить, Q=выход)

**Технологии:** Python Rich library

#### 2.2.2 Orchestrator (Главный контроллер)

**Назначение:** Управление всем процессом сбора данных

**Функции:**
- Чтение Excel файлов (11 файлов, 75,706 товаров)
- Создание и управление 5-10 параллельными сессиями
- Распределение товаров между сессиями (равномерно)
- Отслеживание состояния каждого товара в SQLite
- Обработка ошибок и retry логика
- Сохранение прогресса (можно остановить/продолжить)

**Состояния товара:**
- `pending` - ожидает обработки
- `processing` - в процессе обработки
- `completed` - успешно обработан
- `failed` - ошибка (будет повторная попытка)

#### 2.2.3 Browser Session (Playwright)

**Назначение:** Имитация реального пользователя для одного товара

**Функции:**
- Запуск браузера с уникальным профилем (User-Agent, cookies, fingerprint)
- Каскадный поиск данных по источникам
- Извлечение данных (фото, характеристики, datasheet, описание, цены)
- Человекоподобное поведение (скроллинг, паузы, случайные переходы)
- Сохранение данных в PostgreSQL через Prisma

**Человекоподобное поведение:**
- Задержки 15-30 секунд между запросами к ChipDip
- Задержки 5-10 секунд между запросами к Google
- Задержки 10-20 секунд между запросами к производителям
- Скроллинг страницы (имитация чтения)
- Случайные переходы по сайту (не только товары)
- Перерывы каждые 1-2 часа (5-10 минут)

#### 2.2.4 Data Extractors

**Назначение:** Извлечение данных из разных источников

**ChipDip Extractor:**
- URL: `https://www.chipdip.ru/search?searchtext={partNumber}`
- Извлекает: фото, характеристики, описание на русском, цены, наличие
- Использует существующий `src/lib/parser/product-parser.ts` (после исправления)

**Google Search Extractor:**
- Поиск: `{partNumber} {manufacturer} datasheet filetype:pdf`
- Извлекает: ссылки на PDF datasheet

**Manufacturer Extractor:**
- Определяет сайт производителя по manufacturer name
- Извлекает: официальные характеристики, datasheet, фото

**Distributor Extractor:**
- DigiKey, Mouser, Farnell (без API, через веб-интерфейс)
- Извлекает: характеристики, цены, наличие

## 3. Поток данных

### 3.1 Инициализация

1. Orchestrator читает все 11 Excel файлов
2. Загружает 75,706 артикулов в SQLite с состоянием `pending`
3. Создаёт 5-10 параллельных Browser Sessions
4. Распределяет товары между сессиями равномерно

### 3.2 Обработка одного товара (в одной сессии)

```
1. Получить товар из очереди (состояние: pending → processing)
2. Попытка 1: ChipDip
   ├─ Если найдено → извлечь все данные → сохранить в БД
   └─ Если не найдено → перейти к шагу 3
3. Попытка 2: Google Search (datasheet)
   ├─ Если найдено → сохранить ссылку на datasheet
   └─ Если не найдено → перейти к шагу 4
4. Попытка 3: Сайт производителя
   ├─ Если найдено → извлечь данные → сохранить в БД
   └─ Если не найдено → перейти к шагу 5
5. Попытка 4: Дистрибьюторы (DigiKey, Mouser, Farnell)
   ├─ Если найдено → извлечь данные → сохранить в БД
   └─ Если не найдено → пометить как failed
6. Обновить состояние товара (processing → completed/failed)
7. Задержка (15-30 секунд для ChipDip, 5-20 для других)
8. Перейти к следующему товару
```

### 3.3 Человекоподобное поведение

**Каждая сессия:**
- Работает 1-2 часа, потом перерыв 5-10 минут
- Случайный порядок обработки товаров (не последовательно)
- Имитация "усталости" (замедление к концу сессии)
- Случайные переходы по сайту (главная страница, категории)

**Опционально (можно отключить для ускорения):**
- Ночные перерывы: 23:00-07:00 МСК
- Выходные: работает меньше (имитация хобби)

## 4. База данных

### 4.1 SQLite (отслеживание прогресса)

```sql
CREATE TABLE product_queue (
  id INTEGER PRIMARY KEY,
  part_number TEXT NOT NULL,
  manufacturer TEXT NOT NULL,
  package TEXT,
  status TEXT NOT NULL, -- pending/processing/completed/failed
  session_id INTEGER,   -- какая сессия обрабатывает
  attempts INTEGER DEFAULT 0,
  last_error TEXT,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_status ON product_queue(status);
CREATE INDEX idx_session ON product_queue(session_id);
```

### 4.2 PostgreSQL (финальные данные)

Используем существующую Prisma схему:
- `Product` - основная информация
- `ProductImage` - фотографии
- `Specification` - характеристики (key-value)
- `Datasheet` - PDF ссылки
- `Manufacturer` - производители
- `Category` - категории

### 6.1 Целевые показатели

- **Время:** 10-14 дней (работа 24/7 без ночных перерывов)

### 6.2 Задержки (для предотвращения блокировок)

| Источник       | Задержка между запросами | Обоснование                    |
|----------------|--------------------------|--------------------------------|

- Если одна сессия заблокирована - другие продолжают работать

## 7. Обработка ошибок

### 7.1 Типы ошибок

1. **Блокировка (403, captcha)** - переключение на другой источник
2. **Таймаут** - retry с увеличенной задержкой
3. **Товар не найден** - пробуем следующий источник
4. **Ошибка парсинга** - логируем, пробуем другой источник
5. **Ошибка БД** - retry с экспоненциальной задержкой

### 7.2 Retry логика

- **Максимум 3 попытки** для каждого источника
- **Экспоненциальная задержка:** 1 мин → 5 мин → 15 мин
- После 3 неудачных попыток - переход к следующему источнику
- Если все источники не сработали - пометить как `failed` (будет обработано позже вручную)

### 7.3 Логирование

- **Уровни:** DEBUG, INFO, WARNING, ERROR
- **Файлы логов:** `logs/collector-{date}.log`
- **Ротация:** ежедневно, хранить 30 дней
- **Формат:** JSON для удобного анализа

## 9. Конфигурация

### 9.1 Файл конфигурации (`config.yaml`)

```yaml
# Общие настройки
sessions:
  count: 10                    # Количество параллельных сессий
  work_duration: 7200          # Работа 2 часа (секунды)
  break_duration: 600          # Перерыв 10 минут (секунды)
  night_break: false           # Отключить ночные перерывы (для ускорения)

# Задержки (секунды)
delays:
  chipdip: [15, 30]            # Случайная задержка 15-30 сек
  google: [5, 10]              # Случайная задержка 5-10 сек
  manufacturer: [10, 20]       # Случайная задержка 10-20 сек
  distributor: [10, 15]        # Случайная задержка 10-15 сек

# Retry логика
retry:
  max_attempts: 3              # Максимум 3 попытки
  backoff: [60, 300, 900]      # 1 мин, 5 мин, 15 мин

# Источники данных (приоритет)
sources:
  - name: chipdip
    enabled: true
    priority: 1
  - name: google
    enabled: true
    priority: 2
  - name: manufacturer
    enabled: true
    priority: 3
  - name: distributor
    enabled: true
    priority: 4

# База данных
database:
  sqlite: ./data/progress.db
  postgresql: ${DATABASE_URL}

# Логирование
logging:
  level: INFO
  file: ./logs/collector-{date}.log
  rotation: daily
  retention: 30
```
