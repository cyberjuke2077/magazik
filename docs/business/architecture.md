# Архитектурные решения

## Парсер живёт вне этого репо

Парсер товарной базы - отдельный проект, локально на Mac разработчика.
В этом репозитории его нет и быть не должно.

**Почему:** Парсер тяжёлый (stealth Chromium, Python, прокси), с отдельным циклом разработки.
Смешивать его с магазином - лишняя сложность.

**Следствие:** Не искать парсер в этом репо, не пытаться воссоздать.
Данные из парсера попадают в локальный Docker PostgreSQL,
откуда публикуются в Supabase через `npm run db:publish`.

---

## Архитектура «две БД»

```
Парсер (Mac) → Docker PostgreSQL → db:publish → Supabase (прод)
```

Локальная Docker PostgreSQL - источник правды по каталогу.
Supabase - прод, куда летит готовый каталог. Плюс там живут заявки клиентов.

**Почему:** Enrichment и парсинг - тяжёлые операции с браузерами, прокси, API-квотами.
Запускать это на сервере/Vercel невозможно. Локально удобнее.
В прод летит только чистый результат.

**Следствие:** `QuoteRequest`, `QuoteRequestItem` и `WholesaleLead` живут только
в Supabase. При `db:publish` эти таблицы не входят в публикационную транзакцию.

`db:publish` использует разные роли подключений:

- `DATABASE_URL` - источник каталога;
- `PUBLISH_DATABASE_URL` - отдельная цель на session-порту 5432;
- `DIRECT_URL` - прямое подключение Prisma для migration.

Скрипт останавливается, если источник и цель указывают на одну БД или если цель
использует transaction pooler. До и после публикации он сравнивает количество
записей в трёх клиентских таблицах и сообщает ошибку при любом расхождении.

### Локальный MVP перед Preview

Локальный MVP является обязательным первым рубежом. Команды `dev:local`,
`build:local`, `test:e2e:local`, `db:migrate:local`, `db:seed:local-mvp` и
`db:check:local-mvp` принудительно используют PostgreSQL на `localhost` или
`127.0.0.1`. Скрипты записи завершаются ошибкой для любого удалённого host.

Seed создаёт небольшой детерминированный каталог для полного пользовательского
пути. E2E удаляет только собственные заявки, лиды и rate-limit counters. Команда
`check:db-failure:local` запускает production-сборку с намеренно недоступной
тестовой БД и проверяет нейтральную ошибку в реальном Chromium.

Этот контур не является Preview или production и не разрешает автоматически
применять миграции, публиковать каталог или переносить локальные данные в Supabase.

E2E запускается на детерминированной базе только с тремя seed-товарами. Если в
обычной локальной БД уже есть рабочие данные каталога, для визуальной регрессии
используется отдельная временная локальная БД. Это сохраняет рабочий каталог и
не требует обновлять baseline под случайный набор данных.

Имя временной БД передаётся через `POSTGRES_DB`, а URL формирует
`scripts/with-local-db.ts` из локальных `POSTGRES_*`. Нельзя строить тестовый URL
из `.env` `DATABASE_URL`, потому что он может указывать на Supabase.

### Production health и конфигурация

`GET /api/health` проверяет соединение с PostgreSQL с коротким таймаутом. При
успехе он возвращает только `status` и `database`, а при ошибке отвечает 503 без
connection string и внутренних деталей. Ответ запрещено кэшировать.

`npm run check:production-config -- runtime` проверяет только бесплатное ядро:
production URL, PostgreSQL и сильные admin credentials. R2 и Telegram проверяются
отдельными scope `r2` и `telegram`, поэтому их отложенная настройка не маскирует
готовность основного runtime.

### Защита публичных форм

Форма КП, оптовая форма и вход в админку используют PostgreSQL-счётчики
`SubmissionRateLimit`. Ключ содержит SHA-256 от области, временного окна и
хэшированного идентификатора клиента. Исходные IP, email и телефон в таблицу не
попадают.

Перед записью заявки сервер заново получает товар по `productId` и использует
канонические MPN и название из БД. Подменённые, удалённые, дублированные позиции,
дробные и чрезмерные количества отклоняются.

Структурированные логи публичных форм содержат только тип события, результат,
длительность, id записи и статус уведомления. Публичная страница статуса не
выбирает из БД контактные данные, не индексируется и использует
`Referrer-Policy: no-referrer`.

## Общая облачная БД команды

Для совместной разработки есть отдельный Supabase-проект в `37Lunar's Org`
с общей схемой Prisma. Это integration-среда: разработчики видят одни и те же
таблицы и данные, а миграции проверяются до публикации в production.

Доступ выдаётся персональными приглашениями в организацию Supabase. Роль
`Developer` достаточна для работы с проектом, но не даёт доступ к биллингу и
настройкам организации.

Строки подключения хранятся только в локальных `.env` и Vercel Production env.
В Git не попадают ни пароль БД, ни готовые URL. Локальный Docker PostgreSQL
остаётся изолированной средой для экспериментов без доступа к общей БД.

Production-сайт подключается отдельной ролью `electromagaz_app`. Она не имеет
DDL и superuser-прав: читает каталог и изменяет только таблицы заявок, rate limit
и разрешённые поля товара. Доступ к новым таблицам выдаётся отдельным GRANT после
проверки миграции. Общий пароль `postgres` в Vercel не используется.

Перед миграцией, enrichment или аудитом безопасности обязательно сверять
organization, project ref и назначение среды. Доступ к одноимённому проекту
в другой организации не подтверждает состояние этой integration-базы.

**Следствие:** общая Supabase БД не является подтверждением production deploy.
Переменные Vercel и production Supabase настраиваются и проверяются отдельно.

## Прямой enrichment в Supabase

Enrichment пишет через Prisma в базу из `DATABASE_URL`. Поэтому для
контролируемых прогонов `DATABASE_URL` может указывать на выделенный
Supabase-проект вместо локальной PostgreSQL.

**Ограничение:** перед реальным прогоном обязательно выполнить dry-run и
использовать `--limit`, пока формат входных файлов и запись в целевую базу не
подтверждены. Входом служат файлы поставщика с MPN и брендом, а не CSV-экспорт
готового каталога из `data/parsed`.

**Надёжность:** интерактивная Prisma-транзакция persistence использует таймаут
60 секунд и ожидание 30 секунд, поскольку стандартных 5 секунд недостаточно
для удалённой Supabase. Результат источника сохраняется до перевода записи
журнала в следующий статус. При ошибке Supabase товар остаётся доступным для
повторной обработки, а найденные данные не считаются сохранёнными заранее.

**Соответствие ChipDip:** поисковая выдача считается только списком кандидатов.
Перед сохранением парсер открывает карточку и требует точного совпадения
нормализованного MPN. Вместе с описанием, характеристиками, изображениями и
даташитами сохраняются SKU и вес. URL страницы ChipDip в карточке и provenance
не сохраняется.

**Память и rate limit:** общая Supabase служит памятью enrichment. Карточки
`complete`, обновлённые в пределах срока свежести, по умолчанию не попадают
в новую очередь. Несекретные параметры свежести и задержек хранятся в
`config/enrichment.json`; env может переопределить их на машине оператора.
`--force-refresh` используется только для явного повторного сбора.

**Цена:** публичная цена ChipDip в RUB записывается только в пустое поле или
поверх прежней parser-managed цены. Цена менеджера без provenance имеет
приоритет и не изменяется enrichment.

**Объём:** полный каталог ChipDip не собирается. Владелец передаёт отдельный
файл с нужными MPN и брендами, после чего выполняются dry-run, ограниченный
пилот и resumable-обработка только этого списка.

**Медиа:** перенос изображений и datasheet в целевой бакет отложен. До явного
подтверждения владельца, что бакет подготовлен, миграция и массовая загрузка
файлов не запускаются.

Прямой тестовый прогон не меняет правило production-публикации: подтверждённый
набор каталога попадает в production через проверенный `db:publish`, пока
владелец отдельно не подтвердит смену этого процесса.

## PostgreSQL FTS как поиск MVP

В MVP используется один поисковый контур - PostgreSQL FTS. Он обслуживает
автодополнение `/api/search`, поиск каталога и CSV-экспорт без отдельного
индексатора и дополнительного production-сервиса.

`Product.searchVector` - `tsvector` столбец с весами: MPN (вес A) > название (B)
> описание (C). Он создаётся через raw SQL migration и обновляется триггером.

Meilisearch отложен в post-MVP. Решение можно пересмотреть, если LIVE-метрики на
утверждённом каталоге покажут недостаточное качество опечатко-устойчивого поиска
или неприемлемое время ответа PostgreSQL FTS.

## Stealth Chromium для ChipDip

ChipDip защищён от ботов. Обычный Playwright детектируется.

**Решение:** cloakbrowser - Chromium с антидетект патчами.
`browser-registry.ts` следит за запущенными процессами и закрывает их при shutdown.

**Следствие:** ChipDip - самый медленный источник в enrichment-пайплайне (3-й приоритет).
При soft-block LCSC пайплайн переключается на ChipDip автоматически.

## Ink TUI для enrichment

Enrichment прогоняет тысячи позиций - часами.
Нужна визуализация прогресса прямо в терминале.

**Решение:** Ink (React for CLI) - полноценный интерактивный дашборд в терминале.
Показывает прогресс по источникам, скорость, ошибки, оставшееся время.

Если TUI мешает (CI, редиректы вывода): `npm run enrichment:run -- --no-tui`.

## npm вместо pnpm

AGENTS.md написан для pnpm, но проект переехал на npm.

**Почему:** Vercel нативно работает с npm в текущей конфигурации.
lock-файл: `package-lock.json`.

**Правило:** Никогда не использовать `pnpm` или `yarn` в этом проекте.
Все команды через `npm`.

---

## Cloudflare R2 для картинок

Картинки не в репо и не в Supabase Storage.

**Почему:** R2 дешевле, без egress-fee, хорошо интегрируется с Vercel через CDN.
Бакет общий для локального и прод окружения - разделения нет.

**Следствие:** `ProductImage.imageUrl` - это прямой R2 URL.
Публиковать картинки через `db:publish` не нужно - они уже доступны.

## Vercel для деплоя

Push в `main` запускает Vercel Production deployment.
Production получает sensitive `DATABASE_URL` и `DIRECT_URL`, настроенные вручную
для отдельной runtime-роли общей Supabase-базы.
Preview намеренно не получает production database credentials. Для функционального
Preview нужна отдельная Supabase branch или sandbox и отдельные Preview env.

Текущий target после пересоздания 2026-08-20 - Vercel project
`cyberjuke2077s-projects/electromagaz-production`, ID
`prj_RkTeKu3bIIkImfBTfU11zTzpw8bm`.
Удаление старого project не переносит env и Supabase integration. Их нужно
подключать к новому target отдельно, не копируя credentials в Git.

Каталожные страницы и `sitemap.xml` читают PostgreSQL только во время запроса,
а не во время `next build`. Отсутствие database env не должно ломать сборку,
но database routes без env должны завершаться явной runtime-ошибкой.

`build` в `package.json`:
```bash
prisma generate && next build
```

Prisma generate нужен на каждом билде - Vercel не кэширует node_modules между деплоями надёжно.
