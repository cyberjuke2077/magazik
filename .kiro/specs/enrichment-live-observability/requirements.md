# Requirements Document

Требования: live observability обогатителя (enrichment-live-observability)

## Introduction

Обогатитель `pnpm enrichment:run` (entry point: `src/scripts/enrichment-run.ts`) парсит товары из 11 файлов поставщика (всего 69 116 строк) через цепочку источников ChipDip → LCSC → Mouser. На текущем темпе (~50 MPN/час по ChipDip без прокси) полный обход занимает порядка 50 дней непрерывной работы, поэтому владельцу магазина критично иметь живую панель наблюдения за процессом, а не только постмортем-разбор JSON-логов.

### Текущие симптомы

- При запуске `pnpm enrichment:run` в терминал льётся непрерывный поток JSON-строк, по которым невозможно быстро ответить на вопросы «сколько MPN осталось», «какие найдены на ChipDip, какие нет», «где сейчас находится парсер».
- Команда `pnpm enrichment:status` (`src/scripts/enrichment-status.ts`) даёт статический снимок и не показывает изменений во времени.
- Существующий `progress-reporter.ts` пишет сводку в БД и в консоль раз в 30–60 секунд — этого недостаточно для интерактивного наблюдения.
- Нет агрегированного представления о покрытии: какой процент исходных 69 116 строк уже обработан, какова разбивка по брендам, какова эффективность каждого источника.
- При возникновении проблем (блокировки, не найденные MPN) пользователь узнаёт о них постфактум, листая логи.

### Цели фичи

1. Показывать живой TUI-дашборд в том же терминале, где работает `pnpm enrichment:run` (htop-подобный вид с обновлением раз в секунду).
2. Расширить `pnpm enrichment:status`: богатый одноразовый снапшот, режим `--watch`, разрезы по бренду/unresolved/source-stats.
3. Дать пользователю ответы на ключевые вопросы:
   - сколько MPN осталось из исходных 69 116 строк Excel,
   - какие данные нашёл ChipDip и какие не нашёл,
   - точно ли всё собрано (coverage по описаниям/спекам/datasheet/категории),
   - что происходит в реальном времени.
4. Сохранить совместимость со старым потоком JSON-логов в `logs/enrichment-YYYY-MM-DD.log` для постмортем-разбора.

### Что НЕ в скоупе

- Graceful shutdown CloakBrowser и логика детекции блокировки ChipDip — обрабатываются параллельной спекой `enrichment-shutdown-and-block-detection`.
- Извлечение characteristics с ChipDip — обрабатывается параллельной спекой `fix-chipdip-specs-extraction`.
- Веб-дашборд в браузере, отдельный admin UI — фича только про CLI/TUI.
- Авторизация, мульти-пользовательский доступ к дашборду.

Дизайн архитектуры (выбор библиотеки TUI, схема event-bus, структура подписок) и список задач выносятся в отдельные документы (`design.md`, `tasks.md`).

## Glossary

- **Обогатитель** — CLI-процесс `pnpm enrichment:run` (entry: `src/scripts/enrichment-run.ts`), который парсит товары через цепочку ChipDip → LCSC → Mouser.
- **TUI-дашборд** — интерактивная текстовая панель в терминале (terminal user interface) с обновляемыми блоками вместо потокового лога. Аналоги: `htop`, `docker stats`, `k9s`.
- **MPN** — артикул производителя (Manufacturer Part Number), например `STM32F469ZIT6`.
- **runId** — идентификатор текущего запуска обогатителя, хранится в `ImportProgress`.
- **EnrichmentJournal** — Prisma-модель с per-MPN статусами обогащения (`pending`, `chipdip_done`, `chipdip_not_found`, `chipdip_blocked`, `lcsc_done`, `lcsc_not_found`, `lcsc_blocked`, `mouser_done`, `mouser_not_found`, `mouser_failed`, `mouser_brand_mismatch`, `done`, `unresolved`).
- **ImportProgress** — Prisma-модель с агрегированным состоянием запуска (status, totalProducts, importedProducts, ETA, importSpeed).
- **Excel-источник** — 11 файлов поставщика (10 xlsx + 1 csv), всего 69 116 строк MPN. Эти строки — общий объём, по которому считается остаток.
- **Coverage-метрика** — доля товаров в БД, у которых заполнено целевое поле (description / specs / datasheet / category), от общего числа `Product`-записей.
- **Hit rate источника** — доля MPN, на которых данный источник вернул валидные данные (chipdip_done / total_chipdip_attempts и аналогично для LCSC/Mouser).
- **Event bus обогатителя** — внутренний in-process канал событий оркестратора (EventEmitter или аналог), на который подписывается TUI-рендерер для получения обновлений без опроса БД.
- **Снапшот-источник** — источник данных для команды `enrichment:status` без `--watch`: разовый запрос к БД (Prisma) без подписки на event-bus.
- **TUI-рендерер** — компонент, отвечающий за отрисовку дашборда в терминале (использует ANSI-escape-коды или TUI-библиотеку).
- **Hotkey** — сочетание клавиш, обрабатываемое TUI-рендерером поверх stdin (например `q`, `p`, `?`, `Ctrl+C`).
- **Лента событий** — список последних N (10–20) обработанных MPN с их финальным статусом, отображаемый в дашборде в порядке от нового к старому.
- **JSON-лог** — структурированный лог в `logs/enrichment-YYYY-MM-DD.log`, который пишет существующий `src/lib/enrichment/observability/logger.ts`.
- **Log-mode (legacy-режим)** — режим запуска `pnpm enrichment:run`, в котором TUI отключён и в stdout идёт потоковый JSON-лог (старое поведение).

## Подтверждённые факты (для контекста)

- `src/lib/enrichment/observability/logger.ts` — существующий логгер JSON-событий в файл `logs/enrichment-YYYY-MM-DD.log`. Изменению не подлежит.
- `src/lib/enrichment/observability/progress-reporter.ts` — существующий компонент, обновляющий `ImportProgress` каждые 30 секунд и печатающий сводку в консоль каждые 60 секунд.
- `src/scripts/enrichment-status.ts` — существующий CLI-снапшот по запросу (`pnpm enrichment:status`).
- `EnrichmentJournal` хранит per-MPN статусы (см. Glossary).
- `ImportProgress` хранит агрегированное состояние запуска (runId, status, ETA, importSpeed).
- Полный объём импорта — **69 116 строк** в 11 файлах. Это «знаменатель» для метрики остатка.
- Дефолтная скорость ChipDip — ~50 MPN/час (без прокси, с jitter 15–30 секунд).
- Mouser API — лимит 1000 запросов/день.
- Параллельная спека `enrichment-shutdown-and-block-detection` отвечает за корректный graceful shutdown и детекцию блокировки. Эта спека НЕ дублирует и НЕ подменяет её логику; она лишь корректно реагирует на сигналы Ctrl+C и отображает текущее состояние.

## Requirements

### Требование 1: запуск TUI-дашборда внутри `pnpm enrichment:run`

**User Story:** Как владелец магазина, я хочу при запуске обогатителя видеть в том же терминале живую панель состояния, а не поток JSON-строк, чтобы быстро понимать, что сейчас происходит.

#### Acceptance Criteria

1. WHEN пользователь запускает `pnpm enrichment:run` без флагов отключения TUI, THEN THE Система SHALL отображать в стандартном выводе TUI-дашборд вместо потока JSON-строк.
2. THE Система SHALL обновлять TUI-дашборд с интервалом не более 1 секунды и не реже одного раза в 2 секунды.
3. THE Система SHALL обновлять только изменившиеся блоки экрана (частичная перерисовка через ANSI-escape-коды или TUI-библиотеку), а не очищать и перерисовывать весь экран целиком.
4. WHEN TUI-дашборд активен, THEN THE Система SHALL подавлять вывод JSON-логов в stdout, при этом продолжая запись JSON-логов в файл `logs/enrichment-YYYY-MM-DD.log` без изменений.
5. WHEN stdout не является TTY (например, обогатитель запущен с перенаправлением вывода в файл или в CI), THEN THE Система SHALL автоматически отключить TUI и работать в legacy-режиме потокового JSON-лога без участия пользователя.
6. WHERE задан флаг командной строки `--no-tui` или `--log-mode`, THE Система SHALL запускать обогатитель в legacy-режиме (потоковый JSON-лог в stdout, как до внедрения TUI).
7. IF терминал имеет ширину менее 80 столбцов или высоту менее 20 строк, THEN THE Система SHALL отобразить компактное предупреждение и продолжить работу с урезанным набором блоков (приоритет: прогресс, текущий MPN, счётчики статусов).
8. WHEN TUI-рендерер не может инициализироваться (отсутствует поддержка ANSI, ошибка библиотеки), THEN THE Система SHALL автоматически переключиться в legacy-режим и записать в JSON-лог событие `tui_init_failed` с причиной.

### Требование 2: контент TUI-дашборда — прогресс и метрики

**User Story:** Как владелец магазина, я хочу видеть в дашборде ключевые числа: сколько MPN обработано, сколько осталось, с какой скоростью идёт обработка и когда завершится текущая очередь.

#### Acceptance Criteria

1. THE TUI-дашборд SHALL отображать прогресс-бар с процентом и абсолютными числами в формате `X / Y MPN, Z%`, где `X` — обработано, `Y` — общий объём текущей очереди обогатителя, `Z` — округлённое до целого процента.
2. THE TUI-дашборд SHALL отображать остаток MPN от исходных 69 116 строк Excel в формате `Осталось из Excel: A / 69116 (B%)`, где `A` — число MPN, у которых статус в `EnrichmentJournal` НЕ равен `done` И НЕ равен `unresolved` (или MPN отсутствует в журнале).
3. THE TUI-дашборд SHALL отображать текущий обрабатываемый MPN, его канонический бренд и время старта обработки текущего MPN (в формате `HH:MM:SS` локального времени).
4. THE TUI-дашборд SHALL отображать ETA до окончания обработки текущей очереди обогатителя в формате `D дней HH:MM` или `HH:MM:SS`, рассчитанный на основе текущей скорости.
5. THE TUI-дашборд SHALL отображать скорость обработки в двух единицах: краткосрочную (MPN/мин, скользящее окно последних 5 минут) и долгосрочную (MPN/час, среднее за всё время текущего runId).
6. THE TUI-дашборд SHALL отображать время работы текущего runId (uptime) в формате `D дней HH:MM:SS` или `HH:MM:SS`.
7. THE TUI-дашборд SHALL отображать текущую фазу обогатителя одним из значений: `ChipDip queue`, `LCSC queue`, `Mouser queue`, `idle`, `shutting down`.

### Требование 3: контент TUI-дашборда — счётчики статусов и разбивки

**User Story:** Как владелец магазина, я хочу видеть в дашборде, сколько MPN найдено на каждом источнике и какие бренды обработаны, чтобы оценивать качество и распределение прогресса.

#### Acceptance Criteria

1. THE TUI-дашборд SHALL отображать счётчики по статусам `EnrichmentJournal`: `chipdip_done`, `chipdip_not_found`, `chipdip_blocked`, `lcsc_done`, `lcsc_not_found`, `mouser_done`, `mouser_not_found`, `unresolved`. Каждый счётчик отображается как абсолютное число.
2. THE TUI-дашборд SHALL отображать разбивку по брендам — топ-10 по числу MPN в очереди — с двумя числами для каждого бренда: количество обработанных MPN (статус `done` или `unresolved`) и количество оставшихся (все остальные статусы).
3. THE TUI-дашборд SHALL отображать разбивку по источникам в виде процентов: какая доля обработанных MPN получила данные от ChipDip (`chipdip_done`/`done_total`), какая от LCSC (`lcsc_done`/`done_total`), какая от Mouser (`mouser_done`/`done_total`). Сумма процентов SHALL быть равна 100% с точностью до округления.
4. THE TUI-дашборд SHALL отображать использование Mouser-квоты в формате `Mouser: X / 1000 на сегодня`, где `X` — число запросов к Mouser API за текущий календарный день (UTC).

### Требование 4: контент TUI-дашборда — лента событий

**User Story:** Как владелец магазина, я хочу видеть последние обработанные MPN с их статусами и список последних не найденных артикулов, чтобы быстро диагностировать проблемы.

#### Acceptance Criteria

1. THE TUI-дашборд SHALL отображать ленту последних обработанных MPN: от 10 до 20 строк (точное число определяется в design.md), упорядоченных от нового к старому.
2. THE строка ленты событий SHALL содержать: индикатор результата (например `✓` для `*_done`, `✗` для `*_not_found`, `⚠` для `*_blocked`/`*_failed`), MPN, бренд, финальный статус.
3. THE TUI-дашборд SHALL применять цветовое выделение к строкам ленты: зелёный для `*_done`, красный для `*_not_found`/`unresolved`, жёлтый для `*_blocked`/`*_failed`. WHERE терминал не поддерживает цвета (`NO_COLOR=1` или non-TTY), THE Система SHALL опускать цветовое выделение без падения.
4. THE TUI-дашборд SHALL отображать отдельный блок «Последние не найденные» — список последних 5 MPN со статусами `chipdip_not_found`, `lcsc_not_found`, `mouser_not_found` или `unresolved` с указанием бренда и источника, который вернул not_found.

### Требование 5: hotkeys в TUI-дашборде

**User Story:** Как владелец магазина, я хочу управлять обогатителем горячими клавишами прямо из дашборда, чтобы не открывать второй терминал.

#### Acceptance Criteria

1. WHEN пользователь нажимает клавишу `q` или `Ctrl+C` в активном TUI-дашборде, THEN THE Система SHALL инициировать graceful shutdown обогатителя (делегируя выполнение существующему механизму shutdown, специфицированному в спеке `enrichment-shutdown-and-block-detection`).
2. WHEN пользователь нажимает `Ctrl+C`, THEN THE TUI-рендерер SHALL передать сигнал на shutdown в течение не более 100 миллисекунд от момента нажатия (не блокироваться на ожидании следующего тика рендеринга).
3. WHEN пользователь нажимает клавишу `p` в активном TUI-дашборде, THEN THE Система SHALL переключить состояние обогатителя между «работает» и «приостановлен» (в режиме «приостановлен» новые MPN не извлекаются из очереди, текущий обрабатывающийся MPN дорабатывается до конца).
4. WHEN обогатитель находится в состоянии «приостановлен», THEN THE TUI-дашборд SHALL отображать индикатор паузы в блоке текущей фазы.
5. WHEN пользователь нажимает клавишу `?` в активном TUI-дашборде, THEN THE Система SHALL отобразить overlay-блок со списком всех hotkeys и их назначением. Повторное нажатие `?` или `Esc` SHALL закрывать overlay.
6. THE TUI-рендерер SHALL игнорировать любые другие клавиши (не приводить к падению, не передавать в stdin обогатителя).

### Требование 6: расширенный снапшот `pnpm enrichment:status` (без флагов)

**User Story:** Как владелец магазина, я хочу одной командой получить богатый текстовый снапшот состояния обогатителя без запуска самого парсера, чтобы посмотреть прогресс из любого терминала.

#### Acceptance Criteria

1. WHEN пользователь запускает `pnpm enrichment:status` без флагов, THEN THE Система SHALL вывести в stdout статический текстовый снапшот, содержащий те же блоки, что TUI-дашборд (см. требования 2–4): прогресс, остаток от 69 116, счётчики статусов, разбивка по брендам (топ-10), разбивка по источникам, Mouser-квота, лента последних 10 событий, последние 5 не найденных MPN.
2. THE снапшот SHALL завершаться выводом и не входить в режим обновления (одноразовый вывод).
3. WHEN запущенного обогатителя нет (нет активного `ImportProgress` со статусом `running`), THEN THE Система SHALL вывести метку «Обогатитель не запущен» и продолжить отображать накопленные данные из `EnrichmentJournal` (последний завершённый run).
4. THE снапшот SHALL быть пригодным для копирования в текстовое сообщение (без ANSI-escape-кодов, если stdout не TTY).

### Требование 7: режим `pnpm enrichment:status --watch`

**User Story:** Как владелец магазина, я хочу запустить в отдельном терминале наблюдение за обогатителем без перезапуска самого парсера.

#### Acceptance Criteria

1. WHEN пользователь запускает `pnpm enrichment:status --watch`, THEN THE Система SHALL запустить тот же TUI-дашборд, что и `pnpm enrichment:run` (требования 1–5), но без запуска самого обогатителя — только в режиме наблюдения.
2. WHEN активен `--watch`-режим, THEN THE Система SHALL читать состояние из БД (`ImportProgress`, `EnrichmentJournal`) с интервалом не чаще одного раза в 2 секунды, чтобы не нагружать БД.
3. IF обогатитель не запущен (`ImportProgress.status != 'running'`), THEN THE TUI-дашборд в `--watch`-режиме SHALL отображать индикатор «Не запущен» в блоке текущей фазы, продолжая показывать накопленные данные.
4. WHEN пользователь нажимает `q` или `Ctrl+C` в `--watch`-режиме, THEN THE Система SHALL завершить только команду `enrichment:status`, НЕ затрагивая работающий обогатитель.
5. THE `--watch`-режим SHALL НЕ поддерживать hotkey `p` (пауза), так как watcher не управляет обогатителем. Нажатие `p` SHALL быть проигнорировано без падения.

### Требование 8: режим `pnpm enrichment:status --brand <name>`

**User Story:** Как владелец магазина, я хочу посмотреть детали по конкретному бренду — какие его MPN обработаны, какие нет, какие были последние ошибки.

#### Acceptance Criteria

1. WHEN пользователь запускает `pnpm enrichment:status --brand <name>`, THEN THE Система SHALL вывести разбивку для канонического бренда `<name>` (case-insensitive по сравнению с `Manufacturer.name`).
2. THE вывод SHALL содержать: общее число MPN бренда в очереди, число обработанных (`done`), число unresolved, разбивку по статусам `EnrichmentJournal`.
3. THE вывод SHALL содержать список последних 10 ошибок для этого бренда: MPN, статус (`*_blocked`, `*_failed`, `*_not_found`), timestamp, и (если есть) сообщение ошибки из JSON-лога.
4. IF бренд `<name>` не найден среди известных канонических брендов, THEN THE Система SHALL вывести сообщение «Бренд не найден» и завершиться с кодом возврата 1.
5. THE Система SHALL поддерживать комбинацию `--brand <name> --watch`: тот же набор данных в режиме реального времени с интервалом обновления как в требовании 7.2.

### Требование 9: режим `pnpm enrichment:status --unresolved`

**User Story:** Как владелец магазина, я хочу получить список MPN, которые не удалось обогатить ни одним источником, чтобы обработать их вручную.

#### Acceptance Criteria

1. WHEN пользователь запускает `pnpm enrichment:status --unresolved`, THEN THE Система SHALL вывести список всех MPN, у которых статус в `EnrichmentJournal` равен `unresolved`.
2. THE вывод SHALL содержать для каждого MPN: канонический MPN, оригинальный MPN, канонический бренд, последний источник, который пробовал артикул (`chipdip` / `lcsc` / `mouser`), timestamp последнего обновления.
3. THE вывод SHALL быть упорядочен по timestamp последнего обновления — от свежих к старым.
4. WHEN список содержит более 100 MPN, THEN THE Система SHALL вывести первые 100 и сообщение «показано 100 из N, используйте экспорт для полного списка».
5. WHERE задан флаг `--unresolved --json`, THE Система SHALL вывести полный список в JSON-формате (без обрезки), пригодный для редиректа в файл.

### Требование 10: режим `pnpm enrichment:status --source-stats`

**User Story:** Как владелец магазина, я хочу видеть эффективность каждого источника — насколько часто он находит MPN, насколько быстро отвечает, как часто блокирует.

#### Acceptance Criteria

1. WHEN пользователь запускает `pnpm enrichment:status --source-stats`, THEN THE Система SHALL вывести для каждого из источников (ChipDip, LCSC, Mouser) метрики: hit rate (доля найденных от попыток), средняя длительность ответа (мс), частота блокировок (`*_blocked`/попытки) для ChipDip и LCSC, частота failed (`mouser_failed`/попытки) для Mouser.
2. THE расчёт hit rate SHALL производиться по статусам `EnrichmentJournal`: `chipdip_done` / (`chipdip_done` + `chipdip_not_found` + `chipdip_blocked`), аналогично для LCSC и Mouser.
3. THE расчёт средней длительности ответа SHALL производиться по полю `durationMs` из JSON-лога `logs/enrichment-YYYY-MM-DD.log` за текущий день (или за указанный период, если задан флаг `--period`).
4. WHEN JSON-лог за период недоступен или пуст, THEN THE Система SHALL вывести пометку «нет данных» для соответствующей метрики, но НЕ падать.
5. THE вывод SHALL содержать общую таблицу с одной строкой на источник и колонками: hit rate, среднее время, медиана времени, p95 времени, частота блокировок/failed.

### Требование 11: coverage-метрика по БД

**User Story:** Как владелец магазина, я хочу понимать, точно ли всё собрано — какой процент товаров в БД имеет описание, спеки, datasheet и категорию.

#### Acceptance Criteria

1. THE одноразовый снапшот `pnpm enrichment:status` SHALL содержать блок «Coverage» с долями (в процентах) товаров (`Product`-записей со статусом `enrichmentStatus = 'complete'` или `'partial'`), у которых:
   - заполнено `description` (непустая строка),
   - есть хотя бы одна связанная `Specification`,
   - есть хотя бы один связанный `Datasheet`,
   - `categoryId` указывает на категорию, отличную от `uncategorized`.
2. THE TUI-дашборд при работе обогатителя SHALL отображать тот же блок «Coverage», обновляемый не чаще одного раза в 30 секунд (этот блок дороже остальных по цене БД-запросов).
3. THE расчёт coverage SHALL выполняться через прямые SQL-агрегаты (не через выборку всех `Product`), чтобы не нагружать память при десятках тысяч записей.
4. IF в БД нет записей `Product` со статусом `complete` или `partial`, THEN THE Система SHALL вывести «Coverage: нет обработанных товаров» вместо процентов.

### Требование 12: источник данных для дашборда — event bus и журнал

**User Story:** Как разработчик, я хочу, чтобы дашборд получал актуальное состояние из in-process event-bus, не опрашивая БД каждую секунду, чтобы не нагружать PostgreSQL.

#### Acceptance Criteria

1. THE TUI-дашборд при работе в режиме `pnpm enrichment:run` SHALL получать события (старт обработки MPN, завершение со статусом, изменение фазы, использование Mouser-квоты) из in-process event-bus оркестратора обогатителя.
2. THE event-bus SHALL быть реализован как in-memory подписка (например `EventEmitter` или аналог) без сериализации в БД и без межпроцессного взаимодействия.
3. THE TUI-дашборд при работе в режиме `pnpm enrichment:status --watch` SHALL читать состояние из БД (`ImportProgress`, `EnrichmentJournal`) с интервалом, заданным в требовании 7.2, поскольку обогатитель работает в другом процессе и event-bus недоступен.
4. THE Система SHALL рассчитывать «остаток из 69 116» (требование 2.2) по совместному источнику: общее число строк Excel берётся из конфигурации или из `ImportProgress.totalProducts`, число обработанных — из подсчёта статусов в `EnrichmentJournal`.
5. WHEN общее число строк Excel неизвестно (например, обогатитель ни разу не запускался), THEN THE Система SHALL отображать остаток как `? / 69116` без падения.
6. THE event-bus SHALL быть устойчив к падению подписчика: исключение в TUI-рендерере НЕ SHALL останавливать обогатитель.
7. THE event-bus SHALL поддерживать минимум следующие типы событий: `mpn_started`, `mpn_completed` (с финальным статусом), `phase_changed`, `mouser_quota_used`, `paused`, `resumed`, `shutdown_initiated`.

### Требование 13: совместимость со старым потоком JSON-логов

**User Story:** Как разработчик, я хочу, чтобы JSON-логи в `logs/enrichment-YYYY-MM-DD.log` продолжали писаться без изменений, чтобы существующие инструменты постмортем-разбора работали по-прежнему.

#### Acceptance Criteria

1. THE Система SHALL продолжать писать JSON-логи через существующий `src/lib/enrichment/observability/logger.ts` без изменений формата записи (поля `timestamp`, `level`, `mpn`, `brand`, `source`, `event`, `durationMs`, `error?`, `proxyN?`).
2. THE формат и набор событий JSON-лога SHALL быть совместимы с текущей версией: новые события (например `tui_init_failed`) добавляются, существующие НЕ удаляются и НЕ переименовываются.
3. WHEN активен TUI-дашборд (требование 1.1), THEN THE Система SHALL подавлять только консольный вывод JSON-логов (stdout), но НЕ запись в файл.
4. WHEN активен legacy-режим (`--no-tui` или non-TTY), THEN THE Система SHALL вести себя идентично текущему поведению: JSON-строки в stdout И запись в файл.
5. THE существующий `src/lib/enrichment/observability/progress-reporter.ts` SHALL продолжать обновлять `ImportProgress` в БД с интервалом не реже 30 секунд независимо от режима TUI/legacy. Консольная сводка раз в 60 секунд SHALL быть подавлена в TUI-режиме (её замещает дашборд) и сохранена в legacy-режиме.

### Требование 14: производительность TUI

**User Story:** Как владелец магазина, я хочу, чтобы дашборд не съедал ресурсы и не замедлял сам обогатитель.

#### Acceptance Criteria

1. THE TUI-рендерер SHALL потреблять не более 5% CPU одного ядра в среднем за минуту работы при обновлении раз в секунду.
2. THE TUI-рендерер SHALL потреблять не более 50 МБ RAM сверх базового потребления обогатителя.
3. WHEN число событий в ленте превышает заданный лимит (от 10 до 20 строк), THEN THE Система SHALL отбрасывать самые старые события без накопления неограниченного буфера.
4. THE расчёт coverage-метрики (требование 11) SHALL выполняться не чаще одного раза в 30 секунд, чтобы избежать нагрузки на БД.
5. THE TUI-рендерер SHALL пропускать кадры рендеринга, если предыдущий кадр ещё не дорисован (back-pressure), а не накапливать очередь.
6. THE подписка дашборда на event-bus SHALL быть синхронной и неблокирующей: один обработчик события — это обновление in-memory state, без БД-запросов и сетевых вызовов.

### Требование 15: тестируемость

**User Story:** Как разработчик, я хочу автотесты для логики дашборда и команд статуса, чтобы безопасно вносить изменения.

#### Acceptance Criteria

1. THE Расчёт_Метрик SHALL быть выделен в чистые функции (без зависимостей от БД и stdout) и иметь unit-тесты (Vitest) на: вычисление процента остатка от 69 116, краткосрочной/долгосрочной скорости, ETA, hit rate каждого источника.
2. THE Расчёт_Метрик SHALL иметь property-based тест на инвариант: сумма процентов разбивки по источникам в требовании 3.3 равна 100 ± 1 (с учётом округления) для любого валидного множества входных счётчиков.
3. THE Event_Bus SHALL иметь unit-тест на устойчивость к падению подписчика (требование 12.6): исключение, выброшенное в обработчике, не приводит к остановке обогатителя.
4. THE TUI_Renderer SHALL иметь snapshot-тест на отображение фиксированного состояния (без живого терминала): подаём фиксированный state → получаем фиксированную текстовую матрицу.
5. THE Команды_Status SHALL иметь интеграционные тесты с моком БД на: одноразовый снапшот без флагов, `--brand <name>` (включая ненайденный бренд), `--unresolved` (включая `--json`), `--source-stats` (включая отсутствие JSON-лога за период).
6. THE Hotkeys_Handler SHALL иметь unit-тесты на обработку `q`, `Ctrl+C`, `p`, `?`, неизвестной клавиши (требование 5.6).
7. THE Авто_Детект_TTY SHALL иметь unit-тест: при `process.stdout.isTTY === false` Система SHALL переключиться в legacy-режим (требование 1.5) без участия пользователя.

### Требование 16: исключения из области фичи

**User Story:** Как разработчик проекта, я хочу, чтобы границы этой спеки были чётко определены и не пересекались с параллельными спеками.

#### Acceptance Criteria

1. THE Система SHALL НЕ реализовывать логику graceful shutdown обогатителя — она специфицирована в параллельной спеке `enrichment-shutdown-and-block-detection`. Эта спека лишь вызывает существующий механизм shutdown по hotkey `q`/`Ctrl+C`.
2. THE Система SHALL НЕ реализовывать логику детекции блокировки ChipDip — она специфицирована в той же параллельной спеке. Дашборд лишь отображает статусы `*_blocked` из `EnrichmentJournal`.
3. THE Система SHALL НЕ изменять логику извлечения characteristics с ChipDip — это область спеки `fix-chipdip-specs-extraction`.
4. THE Система SHALL НЕ создавать веб-дашборд в браузере, не вводить отдельный admin UI и не открывать сетевых портов.
5. THE Система SHALL НЕ вводить новых внешних сервисов (Grafana, Prometheus, Datadog и т.п.) — вся observability остаётся в рамках CLI.
6. THE Система SHALL НЕ менять формат существующих JSON-логов (требование 13.2).
