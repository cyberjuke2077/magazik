# Requirements Document

## Введение

Каталог товаров и модель заказа для интернет-магазина Electromagaz. Магазин работает по модели «под заказ» (made-to-order): товары не хранятся на складе, цена часто отсутствует. Покупатель формирует список запроса (корзину) и отправляет его менеджеру для получения коммерческого предложения. Каталог содержит ~62 627 товаров в PostgreSQL, загруженных через enrichment-пайплайн.

## Глоссарий

- **Каталог** — серверный компонент Next.js, отображающий список товаров с пагинацией, поиском и фильтрами
- **Товар** — запись в таблице Product (Prisma), содержащая partNumber, name, description, price и связи с Category и Manufacturer
- **Список_Запроса** — клиентская корзина в localStorage, содержащая выбранные товары и количества
- **QuoteRequest** — модель в БД, сохраняющая отправленный запрос на коммерческое предложение (контактные данные + позиции)
- **Менеджер** — сотрудник, получающий email-уведомление о новом запросе
- **Поисковый_Движок** — PostgreSQL Full-Text Search (tsvector) по полям name, partNumber, description
- **Фильтр** — серверный параметр URL для ограничения выборки по category или manufacturer
- **Пагинатор** — механизм offset-based пагинации с параметрами page и limit в URL

## Требования

### Требование 1: Отображение каталога товаров

**User Story:** Как покупатель, я хочу просматривать каталог товаров с компактными строками, чтобы быстро находить нужные компоненты по маркировке и производителю.

#### Критерии приёмки

1. THE Каталог SHALL отображать товары в виде компактных строк с полями: partNumber (MPN), name, manufacturer, category и срок поставки «2–4 недели»
2. WHEN поле price у Товара равно null, THE Каталог SHALL отображать текст «Цена по запросу» вместо числового значения цены
3. WHEN поле price у Товара содержит числовое значение, THE Каталог SHALL отображать цену в формате с разделителем тысяч и символом валюты «₽»
4. THE Каталог SHALL рендериться как Server Component без загрузки данных на клиенте
5. THE Каталог SHALL загружать данные из PostgreSQL через Prisma ORM в Server Component

### Требование 2: Пагинация каталога

**User Story:** Как покупатель, я хочу перемещаться по страницам каталога, чтобы просматривать все 62 627 товаров без перегрузки браузера.

#### Критерии приёмки

1. THE Пагинатор SHALL отображать 50 товаров на одной странице
2. THE Пагинатор SHALL хранить текущую страницу и лимит в URL-параметрах в формате `?page=N&limit=50`
3. WHEN пользователь переходит на страницу с параметром page=N, THE Каталог SHALL отображать товары со смещением (N-1)*limit
4. WHEN параметр page отсутствует в URL, THE Каталог SHALL отображать первую страницу (page=1)
5. WHEN параметр page содержит значение больше максимального количества страниц, THE Каталог SHALL отображать последнюю доступную страницу
6. THE Пагинатор SHALL отображать общее количество товаров и текущий диапазон (например, «51–100 из 62 627»)

### Требование 3: Полнотекстовый поиск

**User Story:** Как покупатель, я хочу искать товары по маркировке, названию или описанию, чтобы быстро находить конкретные компоненты.

#### Критерии приёмки

1. WHEN пользователь вводит поисковый запрос, THE Поисковый_Движок SHALL выполнять полнотекстовый поиск по tsvector-индексу на полях name, partNumber и description
2. WHEN поисковый запрос передан, THE Каталог SHALL отображать результаты поиска с учётом активных фильтров и пагинации
3. THE Поисковый_Движок SHALL хранить поисковый запрос в URL-параметре `?q=запрос`
4. WHEN поисковый запрос пуст или отсутствует, THE Каталог SHALL отображать все товары без фильтрации по тексту
5. WHEN результаты поиска отсутствуют, THE Каталог SHALL отображать сообщение «Ничего не найдено» с предложением изменить запрос

### Требование 4: Фильтрация по категории и производителю

**User Story:** Как покупатель, я хочу фильтровать товары по категории и производителю, чтобы сузить выборку до нужного типа компонентов.

#### Критерии приёмки

1. THE Каталог SHALL отображать боковую панель с деревом категорий и количеством товаров в каждой категории
2. WHEN пользователь выбирает категорию, THE Каталог SHALL фильтровать товары по выбранной категории через URL-параметр `?category=slug`
3. WHEN пользователь выбирает производителя, THE Каталог SHALL фильтровать товары по выбранному производителю через URL-параметр `?manufacturer=slug`
4. WHEN активны оба фильтра (category и manufacturer), THE Каталог SHALL отображать товары, соответствующие обоим условиям одновременно
5. WHEN фильтр применяется, THE Пагинатор SHALL сбрасывать параметр page на значение 1
6. THE Каталог SHALL выполнять фильтрацию на сервере через SQL-запрос, без загрузки всех 62 627 товаров на клиент

### Требование 5: Добавление товара в список запроса

**User Story:** Как покупатель, я хочу добавлять товары в список запроса, чтобы сформировать перечень компонентов для получения коммерческого предложения.

#### Критерии приёмки

1. THE Каталог SHALL отображать кнопку «Добавить в запрос» для каждого товара
2. WHEN пользователь нажимает кнопку «Добавить в запрос», THE Список_Запроса SHALL сохранять товар с указанным количеством в localStorage браузера
3. WHEN товар уже присутствует в Списке_Запроса, THE Каталог SHALL отображать индикатор «В списке» вместо кнопки добавления
4. THE Список_Запроса SHALL позволять изменять количество товара с учётом минимального заказа (minOrder)
5. THE Список_Запроса SHALL сохранять данные между сессиями браузера через localStorage

### Требование 6: Отправка запроса на коммерческое предложение

**User Story:** Как покупатель, я хочу отправить сформированный список запроса менеджеру, чтобы получить коммерческое предложение с актуальными ценами и сроками.

#### Критерии приёмки

1. WHEN пользователь заполняет форму запроса и нажимает «Отправить», THE QuoteRequest SHALL сохранять запрос в базу данных со статусом «new»
2. WHEN QuoteRequest успешно сохранён, THE QuoteRequest SHALL отправлять email-уведомление Менеджеру с деталями запроса
3. THE QuoteRequest SHALL содержать поля: companyName, inn, contactPerson, phone, email, comment, deliveryAddress, desiredDeliveryDate и список позиций (productId, partNumber, name, quantity)
4. WHEN отправка формы завершается успешно, THE Список_Запроса SHALL очищать localStorage
5. WHEN отправка формы завершается успешно, THE Каталог SHALL перенаправлять пользователя на страницу подтверждения
6. IF сохранение QuoteRequest в БД завершается ошибкой, THEN THE QuoteRequest SHALL отображать сообщение об ошибке и сохранять данные формы для повторной отправки

### Требование 7: Модель данных QuoteRequest

**User Story:** Как менеджер, я хочу видеть все запросы на КП в базе данных, чтобы обрабатывать их и формировать коммерческие предложения.

#### Критерии приёмки

1. THE QuoteRequest SHALL храниться в PostgreSQL как отдельная модель Prisma со связью к позициям (QuoteRequestItem)
2. THE QuoteRequest SHALL содержать поле status с допустимыми значениями: «new», «in_progress», «quoted», «rejected»
3. THE QuoteRequest SHALL содержать временные метки createdAt и updatedAt
4. THE QuoteRequestItem SHALL содержать ссылку на productId, partNumber, name, quantity и запрошенную цену (если была указана)
5. THE QuoteRequest SHALL реализовываться через server action или API route без использования tRPC

### Требование 8: Серверная архитектура и URL-состояние

**User Story:** Как разработчик, я хочу чтобы каталог работал через Server Components и URL-параметры, чтобы обеспечить SEO-индексацию и производительность при 62 627 товарах.

#### Критерии приёмки

1. THE Каталог SHALL передавать все параметры фильтрации, поиска и пагинации через URL query params
2. THE Каталог SHALL рендерить страницу на сервере при каждом изменении URL-параметров
3. THE Каталог SHALL поддерживать прямые ссылки на отфильтрованные результаты (например, `/catalog?category=resistors&page=2&q=100k`)
4. THE Каталог SHALL использовать server actions для мутаций (отправка QuoteRequest) без tRPC
5. WHEN клиентский компонент необходим для интерактивности (поисковая строка, степпер количества), THE Каталог SHALL ограничивать директиву 'use client' минимальным компонентом
