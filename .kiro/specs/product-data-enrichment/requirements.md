# Requirements Document

Требования: обогащение данных о товарах (product-data-enrichment)

## Introduction

В проекте electromagaz (интернет-магазин микроэлектроники) есть товарная база поставщика — **69 116 артикулов** в 11 файлах (10 xlsx + 1 csv) от китайского посредника. По каждому артикулу есть только MPN, бренд и (иногда) корпус. Для витрины этого недостаточно — нужны название, описание, характеристики, datasheet, фотографии.

Стратегия обогащения:

1. Читать артикулы из Excel/CSV-файлов (разная структура заголовков, включая файлы без заголовков).
2. Канонизировать MPN и бренд.
3. **ChipDip — основной источник** (поиск по MPN через `chipdip.ru/search?searchtext={MPN}`, CloakBrowser без прокси, прокси — опциональный fallback). Даёт русские данные: название, описание, характеристики, datasheet, категорию.
4. **LCSC — вторичный источник** (поиск по MPN через `lcsc.com/search?q={MPN}`, CloakBrowser без прокси). Для MPN, не найденных на ChipDip. Даёт: английское описание, datasheet URL, изображения, specs, package, lifecycle.
5. **Mouser API — третичный источник** (бесплатный тариф, 1000 запросов/день). Для MPN, не найденных ни на ChipDip, ни на LCSC. Даёт: английское описание, datasheet URL, lifecycle, package, images, manufacturer.
6. Сохранять результат в существующую БД через Prisma идемпотентным upsert'ом.
7. Поддерживать остановку и возобновление без потери прогресса.

**Nexar API** — НЕ используется активно (бесплатный тариф ≈ 10 запросов, непригоден для 69k артикулов). Упоминается только как потенциальный будущий источник при покупке платного тарифа.

Дизайн архитектуры и список задач выносятся в отдельные документы (`design.md`, `tasks.md`).

## Glossary

- **MPN (Manufacturer Part Number)** — артикул производителя, например `STM32F469ZIT6`.
- **Канонический MPN (mpnNormalized)** — MPN, очищенный от суффиксов упаковки (`-T`, `-RL`, `+T`, `/NOPB`, `-TR`, `/TR`, `/REEL`, конечные `+`), приведённый к верхнему регистру и очищенный от кириллических омоглифов.
- **Канонический бренд** — стандартизованное имя производителя (`MAXIM/美信` → `Maxim Integrated`, `TI/德州仪器` → `Texas Instruments`, `ST` → `STMicroelectronics`).
- **ChipDip** — российский интернет-магазин электроники (chipdip.ru), основной источник русскоязычных данных.
- **LCSC** — международный дистрибьютор электроники (lcsc.com), вторичный источник данных через web scraping. Даёт английские описания, datasheets, изображения, specs, package, lifecycle.
- **Mouser** — международный дистрибьютор электроники (mouser.com), третичный источник данных через бесплатный Search API.
- **CloakBrowser** — npm-пакет `cloakbrowser`, drop-in замена для Playwright со stealth-Chromium. Используется как `import { launch } from 'cloakbrowser'` с опциональным proxy.
- **Обогащение** — процесс получения и сохранения данных о товаре по его MPN+бренду.
- **Idempotent upsert** — операция записи в БД, многократное применение которой даёт тот же результат, что и однократное.
- **Unresolved артикул** — артикул, которому не удалось получить данные ни из одного источника. Запись создаётся в БД с `enrichmentStatus = "unresolved"`.
- **Partial артикул** — артикул, у которого получены не все целевые поля.
- **Provenance** — отметка об источнике, из которого получено каждое поле, и времени получения.
- **Категория-заглушка** — seed-категория «Без категории» (slug: `uncategorized`) для товаров, где категория неизвестна. Необходима, т.к. `Product.categoryId` — NOT NULL.

- **ChipDip работает без прокси через CloakBrowser.** Статус 200, поиск по MPN возвращает результаты, парсер извлекает данные. Проверено 15 мая 2026. Прокси — опциональный fallback.
- **Mouser Search API — бесплатный тариф 1000 запросов/день.** Регистрация на mouser.com/api-search/. Даёт: описание (EN), datasheet URL, lifecycle, package, images, manufacturer.
- **CloakBrowser — npm-пакет, не отдельное приложение.** Установлен в проекте (`cloakbrowser` в package.json). Используется как `import { launch } from 'cloakbrowser'`. Никаких CDP-серверов не нужно.
- **Webshare residential ротатор активен.** Креды из `.env.proxies` (`p.webshare.io:80` + `yyinovqc-N:9feo3p96zxuf`). Используется как опциональный fallback при блокировке.
- **Webshare datacenter (10 IP) — нерабочие.** Все тайм-аутят. Используем только residential (при необходимости).
- **ChipDip снимает блокировку IP примерно через сутки.**
- **Существующий код парсера ChipDip** (`src/lib/parser/product-parser.ts`) уже извлекает: name, partNumber, manufacturer, category, description, specs, datasheets. Вес и изображения отключены в коде. Этот парсер переиспользуется.
- **Существующий proxy-manager** (`src/lib/proxy/proxy-manager.ts`) поддерживает round-robin/random/least-used ротацию. Переиспользуется.
- **Существующий rate-limiter** (`src/lib/parser/rate-limiter.ts`) — переиспользуется.
- **`Product.categoryId` — NOT NULL** в текущей схеме. Нужна seed-категория «Без категории» для товаров без определённой категории.
- **`Datasheet.title` — обязательное поле.** При отсутствии title от источника генерируем как `"${MPN} Datasheet"`.
- **Нет уникального индекса на `(manufacturerId, partNumber)`** — только `@@index`. Новый `@@unique([manufacturerId, mpnNormalized])` будет ключом upsert.

## Оценки производительности

- **ChipDip**: ~3 товара/мин с jitter 15-30с, 1 сессия = ~180/час. Без прокси (по умолчанию).
- **LCSC**: ~6 товаров/мин с jitter 5-10с, 1 сессия = ~360/час. Без прокси.
- **Mouser**: 1000 запросов/день.
- **Оценка распределения**: ~50% найдены на ChipDip (~35k), ~30% оставшихся найдены на LCSC (~20k из 35k), ~20% нуждаются в Mouser (~15k) = 15 дней Mouser.
- **Итого**: полное обогащение ≈ 3-4 недели при непрерывной работе.

## Requirements


### Требование 1: чтение и нормализация Excel/CSV-файлов

**User Story:** Как владелец магазина, я хочу, чтобы пайплайн читал все мои файлы поставщика (69 116 строк, 11 файлов с разной структурой) и приводил артикулы к единому формату, чтобы дальнейший поиск в источниках работал стабильно.

#### Acceptance Criteria

1. WHEN пайплайн запускается с указанием папки входных файлов, THEN THE Система SHALL обработать все файлы с расширениями `.xlsx`, `.xls`, `.csv` в этой папке (включая файлы с битыми именами в кодировке macroman — путь передаётся как абсолютный).
2. WHEN файл содержит строку заголовков, THEN THE Система SHALL извлекать колонки по китайским заголовкам (с учётом вариаций): `型号` или `型号（必填）` → MPN, `品牌` или `品牌（必填）` → бренд, `封装` или `封装（选填）` → корпус (опционально), `批号` или `批号（选填）` → date code (опционально).
3. WHEN первая строка файла содержит данные, похожие на MPN (паттерн: латинские буквы + цифры, длина 3-30 символов, без иероглифов в первой ячейке), THEN THE Система SHALL определить файл как «без заголовков» и интерпретировать колонки позиционно: колонка 1 → MPN, колонка 2 → бренд, колонка 3 → корпус (если есть).
4. IF в файле отсутствует распознаваемая колонка MPN (ни по заголовку, ни по автодетекту), THEN THE Система SHALL пропустить файл и записать в лог имя файла и причину пропуска.
5. WHEN строка с артикулом прочитана, THEN THE Система SHALL применить нормализацию MPN: верхний регистр, удаление суффиксов упаковки из словаря (`+`, `-T`, `-TR`, `-RL`, `/NOPB`, `/TR`, `/REEL`, `/T7`), замена кириллических омоглифов на латинские (`А`→`A`, `В`→`B`, `С`→`C`, `Е`→`E`, `К`→`K`, `М`→`M`, `Н`→`H`, `О`→`O`, `Р`→`P`, `Т`→`T`, `Х`→`X`), при этом ОРИГИНАЛЬНЫЙ MPN сохраняется неизменным для записи в `Product.partNumber`.
6. WHEN строка с артикулом прочитана, THEN THE Система SHALL применить маппинг бренда по таблице (минимум: `MAXIM/美信` → `Maxim Integrated`, `MAXIM` → `Maxim Integrated`, `美信` → `Maxim Integrated`, `TI/德州仪器` → `Texas Instruments`, `TI` → `Texas Instruments`, `德州仪器` → `Texas Instruments`, `ST` → `STMicroelectronics`, `ATMEL` → `Microchip Technology`, `MICROCHIP` → `Microchip Technology`, `ADI` → `Analog Devices`, `XILINX` → `AMD (Xilinx)`, `QUALCOMM` → `Qualcomm`).
7. IF бренд не распознан таблицей маппинга, THEN THE Система SHALL использовать значение из файла как есть и пометить запись флагом `brand_unmapped` для ручного ревью.
8. THE Система SHALL быть идемпотентной по нормализации MPN: `normalize(normalize(x)) == normalize(x)` для любого входа.
9. WHEN все файлы прочитаны, THEN THE Система SHALL построить дедуплицированный список артикулов по ключу `(canonical_brand, canonical_mpn)` и сохранить в очередь обогащения; варианты корпуса и date code при дублях объединяются в массивы.
10. WHILE формируется очередь, THE Система SHALL фиксировать в логе: количество прочитанных строк, количество файлов (с разбивкой: с заголовками / без заголовков), количество дубликатов и количество пропущенных строк.


### Требование 2: ChipDip как основной источник данных через CloakBrowser

**User Story:** Как владелец магазина, я хочу, чтобы система автоматически получала русскоязычные данные о товарах с ChipDip — это основной источник с русскими описаниями, характеристиками и datasheets.

#### Acceptance Criteria

1. THE Система SHALL использовать ChipDip как ПЕРВЫЙ и ОСНОВНОЙ источник данных для каждого артикула.
2. WHEN наступает очередь артикула, THEN THE Система SHALL выполнить поиск на ChipDip по URL `https://www.chipdip.ru/search?searchtext={MPN}` через CloakBrowser БЕЗ прокси (по умолчанию).
3. THE Система SHALL запускать CloakBrowser через `import { launch } from 'cloakbrowser'` (НЕ через `chromium.launch()` из Playwright). Существующий `src/lib/parser/browser-client.ts` использует plain Playwright — для ChipDip используется CloakBrowser.
4. THE Система SHALL поддерживать формат `CHIPDIP_PROXY_TEMPLATE` для residential-ротаторов вида `http://yyinovqc-{N}:9feo3p96zxuf@p.webshare.io:80`, где `{N}` — случайное целое число из диапазона `CHIPDIP_PROXY_USER_RANGE` (по умолчанию 1..20000). Прокси используется ТОЛЬКО как fallback при блокировке.
5. THE Система SHALL работать без прокси по умолчанию. WHEN `CHIPDIP_PROXY_TEMPLATE` не задан и обнаружена блокировка (403), THEN THE Система SHALL приостановить ChipDip-очередь на 2-4 часа и повторить попытку без прокси. Прокси — опциональный fallback, не обязательный.
6. WHEN пайплайн стартует, THE Система SHALL выполнить health-check: открыть `https://www.chipdip.ru/search?searchtext=STM32F469ZIT6` и проверить HTTP 200 + наличие результатов поиска.
7. IF health-check возвращает 403 / CAPTCHA / редирект на блокировку И прокси задан, THEN THE Система SHALL переключиться на прокси и повторить health-check. IF прокси не задан, THEN THE Система SHALL завершиться с рекомендацией перезапустить через сутки.
8. THE Система SHALL соблюдать задержку между запросами к ChipDip от 15 до 30 секунд (рандомизированный jitter).
9. THE Система SHALL применять меры антидетекции: рандомизировать viewport size при каждой новой сессии, блокировать загрузку ненужных ресурсов (images, fonts, stylesheets) для снижения трафика и fingerprint, ротировать User-Agent при каждой новой сессии.
10. THE Система SHALL соблюдать лимит не более 180 запросов/час с одного IP без прокси.
11. WHEN страница поиска ChipDip содержит результат, THEN THE Система SHALL перейти на страницу товара и извлечь данные, переиспользуя логику из `src/lib/parser/product-parser.ts` (Cheerio): русский заголовок, описание, характеристики (key/value), ссылки на datasheet (PDF), категорию из breadcrumbs. Вес и изображения НЕ извлекаются (отключены в парсере).
12. IF на странице поиска ChipDip нет результатов по MPN, THEN THE Система SHALL пометить артикул `chipdip_not_found` и передать его в очередь LCSC.
13. IF ChipDip возвращает 403 / CAPTCHA в процессе работы, THEN THE Система SHALL пометить артикул `chipdip_blocked` и: (а) если прокси задан — переключиться на прокси, ротировать `{N}`, пауза 30 минут; (б) если прокси не задан — приостановить ChipDip-очередь на 2-4 часа, затем повторить без прокси.
14. THE Система SHALL логировать каждое подключение к ChipDip (URL, статус, длина body, режим: direct/proxy, N в шаблоне прокси если используется).
15. THE Система SHALL поддерживать одновременно не более `CHIPDIP_CONCURRENCY` (дефолт 1, максимум 3) сессий CloakBrowser.
16. THE Система SHALL переиспользовать существующий `src/lib/proxy/proxy-manager.ts` для ротации прокси и трекинга здоровья (при использовании прокси).


### Требование 3: LCSC как вторичный источник данных через CloakBrowser

**User Story:** Как владелец магазина, я хочу, чтобы для артикулов, не найденных на ChipDip, система получала данные с LCSC — это бесплатный источник с английскими описаниями, datasheets, изображениями и характеристиками, доступный без API-ключа.

#### Acceptance Criteria

1. THE Система SHALL использовать LCSC как ВТОРИЧНЫЙ источник — только для артикулов со статусом `chipdip_not_found`.
2. WHEN артикул помечен `chipdip_not_found`, THEN THE Система SHALL добавить его в очередь LCSC для обработки.
3. WHEN наступает очередь артикула в LCSC-очереди, THEN THE Система SHALL выполнить поиск на LCSC по URL `https://www.lcsc.com/search?q={MPN}` через CloakBrowser БЕЗ прокси.
4. THE Система SHALL запускать CloakBrowser для LCSC через `import { launch } from 'cloakbrowser'` без proxy (подтверждено: LCSC доступен без прокси, статус 200, 125 КБ HTML).
5. WHEN страница поиска LCSC содержит результат, THEN THE Система SHALL извлечь данные: английское описание, URL datasheets (PDF), URL изображений товара, характеристики (specs), package, lifecycle status.
6. IF на странице поиска LCSC нет результатов по MPN, THEN THE Система SHALL пометить артикул `lcsc_not_found` и передать его в очередь Mouser API.
7. WHEN из LCSC получен валидный результат, THEN THE Система SHALL пометить артикул `lcsc_done` и НЕ передавать его в очередь Mouser (Mouser пропускается).
8. THE Система SHALL соблюдать задержку между запросами к LCSC от 5 до 10 секунд (рандомизированный jitter).
9. THE Система SHALL поддерживать не более 1 сессии CloakBrowser для LCSC (concurrency = 1).
10. IF LCSC возвращает 403 / блокировку в процессе работы, THEN THE Система SHALL пометить артикул `lcsc_blocked`, приостановить LCSC-очередь на 1 час и повторить попытку.
11. THE Система SHALL логировать каждое подключение к LCSC (URL, статус, длина body).
12. THE Система SHALL обеспечивать скорость LCSC-обогащения ~360 артикулов/час при 1 сессии (с учётом jitter 5-10с).


### Требование 4: Mouser API как третичный источник

**User Story:** Как владелец магазина, я хочу, чтобы для артикулов, не найденных ни на ChipDip, ни на LCSC, система получала данные из Mouser API — это бесплатный источник с английскими описаниями, lifecycle-статусом и фотографиями.

#### Acceptance Criteria

1. THE Система SHALL использовать Mouser Search API как ТРЕТИЧНЫЙ источник — только для артикулов со статусом `lcsc_not_found`.
2. WHEN артикул помечен `lcsc_not_found`, THEN THE Система SHALL добавить его в отдельную очередь Mouser для обработки.
3. THE Система SHALL отправлять POST-запрос к `https://api.mouser.com/api/v1/search/partnumber` с телом `{ "SearchByPartRequest": { "mouserPartNumber": "{MPN}", "partSearchOptions": "" } }` и query-параметром `apiKey={MOUSER_API_KEY}`.
4. WHEN Mouser возвращает результаты, THEN THE Система SHALL выбрать первый результат, у которого `Manufacturer` (после нормализации) совпадает с каноническим брендом артикула (case-insensitive).
5. WHEN из Mouser получен валидный результат, THEN THE Система SHALL извлечь поля: `Description` (английское описание), `DataSheetUrl`, `LifecycleStatus`, `Mouser Part Number`, `ProductDetailUrl`, `ImagePath`, `ManufacturerPartNumber`, `Category`.
6. IF среди результатов Mouser нет совпадения по бренду, THEN THE Система SHALL пометить артикул `mouser_brand_mismatch` и НЕ записывать чужие данные.
7. IF Mouser возвращает пустой результат, THEN THE Система SHALL пометить артикул `mouser_not_found`.
8. THE Система SHALL соблюдать лимит 1000 запросов в день к Mouser API. При достижении лимита THE Система SHALL остановить Mouser-очередь до следующего календарного дня (00:00 UTC) и продолжить обработку других очередей.
9. IF Mouser возвращает HTTP 429 или ошибку квоты, THEN THE Система SHALL остановить Mouser-очередь до следующего дня.
10. IF Mouser возвращает HTTP 5xx или сетевую ошибку, THEN THE Система SHALL повторить запрос до 3 раз с интервалом 5/15/45 секунд, затем пометить артикул `mouser_failed`.
11. THE Система SHALL хранить ключ `MOUSER_API_KEY` ТОЛЬКО в `.env`, никогда в коде или логах.
12. THE Система SHALL выполнять запросы к Mouser последовательно (concurrency = 1) с задержкой 1 секунда между запросами для соблюдения rate limit.
13. THE Система SHALL вести счётчик запросов к Mouser за текущий день и сохранять его в журнале для resume (при перезапуске пайплайна в тот же день — не превышать оставшуюся квоту).

### Требование 5: запись в БД с идемпотентным upsert

**User Story:** Как владелец магазина, я хочу, чтобы данные сохранялись без дублей и чтобы повторный прогон пайплайна не ломал то, что уже импортировано или то, что я отредактировал вручную.

#### Acceptance Criteria

1. THE Система SHALL хранить товары в существующей Prisma-схеме (`Product`, `Manufacturer`, `Category`, `ProductImage`, `Specification`, `Datasheet`, `ImportProgress`).
2. WHEN из источника получены данные о товаре, THEN THE Система SHALL выполнить upsert `Product` по уникальному ключу `@@unique([manufacturerId, mpnNormalized])`.
3. WHEN бренд встречается впервые, THEN THE Система SHALL создать запись `Manufacturer` (slug = lower-kebab от `name`).
4. WHEN категория из ChipDip (breadcrumbs) встречается впервые, THEN THE Система SHALL создать запись `Category` с русским названием и slug из транслитерации.
5. WHEN категория из LCSC или Mouser встречается впервые, THEN THE Система SHALL создать `Category` с английским названием и пометкой `nameNeedsReview = true` для ручного перевода.
6. WHEN категория товара неизвестна (ни один источник не дал категорию), THEN THE Система SHALL присвоить товару seed-категорию «Без категории» (slug: `uncategorized`). Эта категория SHALL быть создана при первом запуске пайплайна (seed).
7. WHEN товар получает характеристики, THEN THE Система SHALL заменить набор `Specification` полным списком (delete-then-insert в одной транзакции).
8. WHEN товар получает datasheets, THEN THE Система SHALL заменить набор `Datasheet` полным списком. Поле `Datasheet.title` SHALL генерироваться как `"${MPN} Datasheet"` если источник не предоставил title. Для записей из ChipDip `language = "ru"`, для записей из LCSC или Mouser `language = "en"`.
9. WHEN товар получает изображения (из LCSC или Mouser), THEN THE Система SHALL заменить набор `ProductImage` для этого товара полным списком из источника (delete-then-insert), сохраняя только URL без локального скачивания.
10. IF после прохода всех источников НИ ОДНО поле не получено (ни ChipDip, ни LCSC, ни Mouser ничего не дали), THEN THE Система SHALL создать запись `Product` с `name = "${Brand_Canonical} ${Original_MPN}"`, `enrichmentStatus = "unresolved"`, `description = "Нет данных"`, `categoryId = uncategorized_category_id`.
11. THE Система SHALL НЕ записывать `Product.weight`, `Product.price`, `Product.priceWholesale`, `Product.inStock`, `Product.stockCount`, `Product.featured`, `Product.tags`, `Product.minOrder` из источников — эти поля остаются под ручным контролем оператора.
12. THE Система SHALL хранить provenance: для каждого поля товара — отметку, из какого источника оно взято и когда. Хранится в JSON-поле `Product.enrichmentMeta`.
13. WHEN существует запись `Product` с тем же ключом и более «сильным» источником на каком-то поле (ChipDip (4) > LCSC (3) > Mouser (2) > заглушка-supplier (1)), THEN THE Система SHALL НЕ перезаписывать это поле менее сильным источником. При равной силе — последний выигрывает.
14. THE Система SHALL генерировать `Product.slug` детерминированно из `Brand_Canonical` и `Canonical_MPN` (kebab-case, ASCII).
15. WHEN persistence запускается дважды на одном и том же `Enrichment_Result`, THEN финальное состояние БД SHALL быть идентичным однократному запуску (идемпотентность).


### Требование 6: расширение схемы Prisma

**User Story:** Как разработчик, я хочу хранить метаданные обогащения, чтобы видеть состояние каждого товара и не терять историю источников при перезапусках.

#### Acceptance Criteria

1. THE Система SHALL добавить в модель `Product` поле `mpnNormalized: String` и создать уникальный составной индекс `@@unique([manufacturerId, mpnNormalized])` — это ключ upsert.
2. THE Система SHALL добавить в модель `Product` поле `lifecycle: String?` (например `Active`, `EOL`, `NRND`).
3. THE Система SHALL добавить в модель `Product` поле `package: String?` (например `SOIC-8`).
4. THE Система SHALL добавить в модель `Product` поле `lastEnrichedAt: DateTime?`.
5. THE Система SHALL добавить в модель `Product` поле `enrichmentStatus: String` (значения: `complete`, `partial`, `unresolved`).
6. THE Система SHALL добавить в модель `Product` поле `enrichmentMeta: Json?` для хранения provenance и пометок (`unmappedBrand`, `multiplePackages`, `descriptionLanguage`, и т.д.).
7. THE Система SHALL добавить в модель `Category` поле `nameNeedsReview: Boolean @default(false)`.
8. THE Система SHALL создать seed-категорию «Без категории» (slug: `uncategorized`) в миграции или seed-скрипте, чтобы гарантировать NOT NULL constraint на `Product.categoryId`.
9. THE Система SHALL вносить изменения через миграцию Prisma (`pnpm db:migrate`), а не правкой `schema.prisma` без миграции.

### Требование 7: фотографии — стратегия по умолчанию

**User Story:** Как владелец магазина, я хочу не тратить дисковое пространство на хранение фото товаров, но иметь изображения из LCSC и Mouser для витрины.

#### Acceptance Criteria

1. THE Система SHALL по умолчанию сохранять только `imageUrl` со стороны источника (LCSC CDN, Mouser CDN и т.п.).
2. THE Система SHALL отдавать эти URL фронтенду через `next/image` (Next.js делает прокси, кеш и ресайз).
3. THE Система SHALL добавлять домены источников в `next.config.ts → images.remotePatterns` при первой встрече нового домена (или документировать список доменов в README).
4. THE Image_Resolver SHALL выполнять HTTP HEAD по каждому URL изображения и сохранять только URL с `Content-Type: image/*` и статусом 200 (битые URL отбрасываются).
5. THE Система SHALL сохранять минимум 1 и максимум 10 изображений на товар, упорядоченных по `ProductImage.order` (0 — первичное).
6. THE Datasheet_Resolver SHALL выполнять HTTP HEAD по каждому URL datasheet и сохранять только URL с `Content-Type: application/pdf` и статусом 200.
7. WHEN ChipDip является источником, THEN THE Система SHALL НЕ извлекать изображения (отключено в парсере из-за водяных знаков). Изображения берутся из LCSC или Mouser.


### Требование 8: прогресс и возобновление

**User Story:** Как владелец магазина, я хочу видеть прогресс импорта и иметь возможность остановить и продолжить пайплайн без потери проделанной работы (учитывая, что полный цикл занимает 3-4 недели).

#### Acceptance Criteria

1. THE Система SHALL использовать существующую модель `ImportProgress` для общего состояния запуска (status, totalProducts, importedProducts, failedProducts, importSpeed, ETA).
2. THE Система SHALL вести отдельную таблицу `EnrichmentJournal` статусов по каждому артикулу: `pending`, `chipdip_done`, `chipdip_not_found`, `chipdip_blocked`, `lcsc_done`, `lcsc_not_found`, `lcsc_blocked`, `mouser_queued`, `mouser_done`, `mouser_not_found`, `mouser_failed`, `mouser_brand_mismatch`, `done`, `unresolved`.
3. WHEN пайплайн прерывается (Ctrl+C, краш, выключение), THEN при следующем запуске THE Система SHALL продолжить с артикулов, у которых статус не равен терминальному (`done`, `unresolved`).
4. THE Система SHALL обновлять `ImportProgress` не реже одного раза в 30 секунд во время работы.
5. THE Система SHALL предоставлять CLI-команду для просмотра текущего прогресса (`pnpm tsx src/scripts/enrichment-status.ts`).
6. THE Система SHALL сохранять счётчик использованных Mouser-запросов за текущий день в журнале, чтобы при перезапуске не превысить дневной лимит 1000.


### Требование 9: безопасность и секреты

**User Story:** Как владелец магазина, я хочу быть уверен, что мои API-ключи не утекают.

#### Acceptance Criteria

1. THE Система SHALL читать `MOUSER_API_KEY`, `CHIPDIP_PROXY_URL` (опционально), `CHIPDIP_PROXY_TEMPLATE` (опционально), `CHIPDIP_PROXY_USER_RANGE`, `CHIPDIP_CONCURRENCY` ИСКЛЮЧИТЕЛЬНО из переменных окружения (`.env`).
2. THE Система SHALL НИКОГДА не печатать `MOUSER_API_KEY`, пароль прокси или другие секреты полностью в логи (допустимо первые 4–6 символов и остальное `***`).
3. THE Система SHALL гарантировать, что `.env`, `.env.local`, `.env.proxies` присутствуют в `.gitignore`.
4. THE `.env.example` SHALL содержать ключи с placeholder-значениями (включая `MOUSER_API_KEY=your_mouser_api_key`, `CHIPDIP_PROXY_TEMPLATE=` (пустое, опционально)).

### Требование 10: производительность и параллелизм

**User Story:** Как владелец магазина, я хочу, чтобы импорт ~69 000 артикулов завершился за разумное время с учётом ограничений источников.

#### Acceptance Criteria

1. THE Система SHALL по умолчанию запускать `CHIPDIP_CONCURRENCY=1` сессию CloakBrowser (настраивается до 3).
2. THE Система SHALL обрабатывать Mouser-очередь последовательно (1 запрос/сек, до 1000/день).
3. WHEN общая длина очереди превышает 10 000, THEN THE Система SHALL обрабатывать её батчами по 500 артикулов с фиксацией прогресса в `ImportProgress` после каждого батча.
4. THE Система SHALL писать в БД пакетами по 50 артикулов (одна транзакция на пакет).
5. WHILE импорт активен, THE использование оперативной памяти Node-процесса SHALL не превышать 1 ГБ при 69 000 артикулов (потоковая обработка через генераторы).
6. THE Система SHALL обеспечивать скорость ChipDip-обогащения ~180 артикулов/час при 1 сессии (с учётом jitter 15-30с, без прокси).
7. THE Система SHALL обеспечивать скорость LCSC-обогащения ~360 артикулов/час при 1 сессии (с учётом jitter 5-10с, без прокси).
8. THE Система SHALL поддерживать параллельную работу ChipDip-очереди, LCSC-очереди и Mouser-очереди (разные артикулы обрабатываются одновременно разными источниками).


### Требование 11: наблюдаемость

**User Story:** Как владелец магазина, я хочу видеть, что и когда происходит, и понимать причину любой ошибки.

#### Acceptance Criteria

1. THE Система SHALL писать структурированные логи в JSON-формате (одна строка — одно событие) в `./logs/enrichment-YYYY-MM-DD.log`.
2. THE log SHALL содержать поля: `timestamp`, `level`, `mpn`, `brand`, `source` (chipdip/lcsc/mouser), `event`, `durationMs`, `error?`, `proxyN?`.
3. THE Система SHALL выводить в консоль human-friendly сводку каждые 60 секунд: обработано X / всего Y, скорость Z/мин, ChipDip-done A, LCSC-done B, Mouser-done C, unresolved D, blocked E, Mouser-квота сегодня F/1000.
4. THE Система SHALL по завершении генерировать отчёт `./logs/enrichment-report-YYYY-MM-DD.json` со статистикой и списком unresolved-артикулов.

### Требование 12: тестирование

**User Story:** Как разработчик, я хочу автотесты ключевой логики, чтобы безопасно вносить изменения.

#### Acceptance Criteria

1. THE MPN_Normalizer SHALL иметь property-based тесты на идемпотентность `normalize(normalize(x)) == normalize(x)` (минимум 200 случайных входов, включая китайские иероглифы, кириллические омоглифы, пробелы, пустые строки).
2. THE Brand_Mapper SHALL иметь unit-тесты на каждое правило словаря и тест на возврат исходного значения при отсутствии в словаре с флагом `brand_unmapped`.
3. THE Deduplicator SHALL иметь тест: для одного и того же набора `Supplier_Row` повторный вызов даёт одинаковое множество `Part_Identity`.
4. THE Persistence_Service SHALL иметь интеграционный тест на идемпотентность upsert: двукратный вызов с одним результатом приводит к одной записи в БД с теми же значениями.
5. THE Excel_Importer SHALL иметь unit-тест на чтение фикстуры с китайскими заголовками, фикстуры без заголовков (автодетект), и пропуск строк без MPN.
6. THE Mouser_Client SHALL иметь unit-тесты с замоканным `fetch` на: успешный ответ, 429 (остановка очереди), пустой результат, brand mismatch.
7. THE ChipDip_Client SHALL иметь интеграционный тест с фикстурой HTML-страницы товара ChipDip (переиспользуя `product-parser.ts`), проверяющий извлечение полей.
8. THE Header_Autodetect SHALL иметь unit-тест на файл с заголовками и файл без заголовков (первая строка — данные).
9. THE LCSC_Client SHALL иметь интеграционный тест с фикстурой HTML-страницы товара LCSC, проверяющий извлечение полей (описание, datasheets, images, specs).


### Требование 13: исключения из области фичи

**User Story:** Как разработчик проекта, я хочу, чтобы эта фича не вводила новых стеков без явного согласия и чётко определяла границы.

#### Acceptance Criteria

1. THE Система SHALL НЕ использовать Nexar API активно (бесплатный тариф ≈ 10 запросов, непригоден для 69k артикулов). Nexar остаётся как потенциальный будущий источник при покупке платного тарифа — код интеграции НЕ реализуется в этой фиче.
2. THE Система SHALL НЕ устанавливать и НЕ использовать Meilisearch (хотя `AGENTS.md` его упоминает, фактически он не подключён).
3. THE Система SHALL НЕ вводить tRPC (CLI-скрипты + существующие API-роуты достаточны).
4. THE Система SHALL НЕ скачивать и НЕ хранить медиа-файлы (фото, datasheets) локально или в S3. Хранение URL — единственная стратегия.
5. THE Система SHALL НЕ переводить английский `Description` из LCSC или Mouser на русский автоматически. Если ChipDip недоступен и русского описания нет — записываем английское описание и помечаем `descriptionLanguage = "en"` для последующего ручного редактирования.
6. THE Система SHALL НЕ использовать Octopart web scraping (заблокирован CloudFlare, 403).
7. THE Система SHALL НЕ использовать AllDatasheet или FindChips как отдельные источники (LCSC покрывает их данные).
8. ANY дальнейшая интеграция Nexar (платный тариф) или других источников SHALL потребовать отдельного спека.

## Принятые решения

Все ключевые решения зафиксированы:

1. **Основной источник — ChipDip** (вместо Nexar). Причина: Nexar free tier ≈ 10 запросов, непригоден. ChipDip даёт русские данные, парсер уже написан.
2. **Вторичный источник — LCSC** (lcsc.com). Бесплатно, без API-ключа, через CloakBrowser без прокси. Даёт английские данные, datasheets, изображения, specs, lifecycle.
3. **Третичный источник — Mouser API** (1000/день бесплатно). Для MPN, не найденных ни на ChipDip, ни на LCSC. Даёт английские данные, lifecycle, фото.
4. **Nexar исключён из активного использования.** Код интеграции не реализуется. При покупке платного тарифа — отдельный спек.
5. **CloakBrowser для ChipDip и LCSC** — `import { launch } from 'cloakbrowser'`. НЕ plain Playwright из `browser-client.ts`.
6. **Прокси — опциональный fallback, не обязательный.** CloakBrowser проходит без прокси на ChipDip и LCSC. При блокировке (403) — автоматическое переключение на прокси (если задан) или пауза 2-4 часа.
7. **Octopart web scraping исключён** (403 от CloudFlare).
8. **Автодетект файлов без заголовков** — по паттерну первой строки (MPN = латиница+цифры vs иероглифы заголовков).
9. **Seed-категория «Без категории»** — решает NOT NULL constraint на `Product.categoryId`.
10. **`Datasheet.title` генерируется** как `"${MPN} Datasheet"` при отсутствии title от источника.
11. **Upsert по `@@unique([manufacturerId, mpnNormalized])`** — новый уникальный индекс, т.к. текущий `@@index` не уникален.
12. **Каскадная логика**: ChipDip first → not found → LCSC → not found → Mouser queue → not found anywhere → stub (unresolved).
13. **Длительность**: 3-4 недели непрерывной работы. Пайплайн рассчитан на многодневный запуск с resume.
14. **Вес** — не собираем, оставляем `null`, заполняется вручную.
15. **Цены** — не собираем, оператор выставляет вручную.
16. **Изображения** — из LCSC или Mouser (ChipDip-изображения с водяными знаками, отключены в парсере).
17. **Provenance приоритет**: ChipDip (4) > LCSC (3) > Mouser (2) > supplier-stub (1).

## Известные внешние ограничения

- **ChipDip** работоспособен через CloakBrowser без прокси. При блокировке — пауза 2-4 часа или переключение на прокси (если задан). При длительной блокировке — перезапуск через сутки.
- **LCSC** работоспособен через CloakBrowser без прокси. Jitter 5-10с, ~360/час.
- **Mouser** — жёсткий лимит 1000 запросов/день. При ~15k артикулов в Mouser-очереди = 15 дней.
- **Webshare residential** — ротация через `yyinovqc-N` (N от 1 до ~20000). Опциональный fallback при блокировке ChipDip.
- **Webshare datacenter** (10 IP) — нерабочий, не используем.
- **Nexar free tier** — ~10 запросов, непригоден для массового использования.
- **Octopart** — заблокирован CloudFlare (403), не используем.
- **AllDatasheet, FindChips** — доступны, но не используем как отдельные источники (LCSC покрывает).
